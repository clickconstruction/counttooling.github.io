## How this map was made, and how to refresh it

1. **Measured, not read.** `npm run build:projectmap` ([scripts/build-projectmap.js](scripts/build-projectmap.js), on [scripts/lib/project-map.js](scripts/lib/project-map.js)) writes `project-map/` (gitignored) in a few seconds: every file's kind, size and load order; the `window.App` registry as a graph (registrations, readers, guarded hooks, load-time reads, spec and script readers); `state.*` reads and writes; DOM ids by owning modal; every function of 20+ lines (named listeners included) by `app.js` SECTION; the specs and node tests that pin each file; churn since this map's head (the marker above); near-duplicate blocks; registry hygiene (unread names, hooks nobody registers). **Run it before planning a split.** `--check` (in `npm run check`) holds three invariants: a Files row for every shell script and feature file, no load-time `App` read of a name a later script registers, no unguarded read of a name nothing registers.
2. **Judged in shards.** Eight agents, one per area, each read a fact packet cut from that skeleton (8 to 27 KB) and only the code it pointed at, and returned a verdict per file, opportunities with evidence, defects, and the places the skeleton misled them (most are fixed in the generator now; see the last section).
3. **Adversarially checked.** One skeptic per shard re-read the code behind every opportunity of 40+ lines, every dedupe and deletion, and every bug or latent defect, and tried to refute it. Each item below carries its result: **confirmed**, **adjusted** (partly right; yield or risk corrected) or **unchecked** (small items, not sent). One defect was refuted and is dropped.
4. **Synthesized** into the ranked list, patterns and sequencing below; contradictions between shards were settled by reading the code.

Cost, for the next time: 17 agents, about 4.0M subagent tokens, 1,235 tool calls, 32 minutes. The estimate before the run was 0.4 to 0.6M; the skeptic pass and the depth of the reads are most of the difference. A refresh that only re-judges areas the skeleton shows changing is the cheaper next pass.

## 8. The skeleton's blind spots

The shards reported where the measured packet misled them. Fixed in the generator after this run: `App` read through a local alias (`const A = window.App`); `state` written through `S()`, `st` or `ctx.getState()`; spec and script readers of a registered name (live spec seams no longer look dead); anonymous listeners named by target and event (the 327-line `document:keydown` is now visible); `App.x = null` no longer counts as a registration; ids a file creates in its own markup are labelled, not reported missing; duplicate runs that differ only in how they reach `state` now match. Still open, worth doing when the map is next refreshed:

- Near-duplicates that differ by a renamed local or reformatting (the page to JPEG to jsPDF block, 9 copies; the water/duct polyline kernels; the intake hydrators) need token-level normalization, not line matching.
- Seam modules (`create*(ctx)` / `createCanvasDraw(deps)`) couple through `ctx.` and `deps.` keys and the report.js `window.*` contract; the registry graph does not see either. Count those keys.
- Spec pinning misses specs that drive a module through a feature or an `App.__*` debug seam, and counts comment mentions as pins.
- Big top-level literals (tour STEPS, LESSONS, CHAPTERS, the screenshot SHOTS catalogue) are most of those files and are invisible to the function table.
- Per-SECTION sizes at the baseline, the `if (SUPABASE_ENABLED)` block that wraps ten SECTIONs, and computed-key state writes (`state[key] = …`) are not measured.
- styles.css gets only line counts; re-declared selectors and unused classes would be the useful measures.
