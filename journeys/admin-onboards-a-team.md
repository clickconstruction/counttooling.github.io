## Open questions for the Phase-2 walk

- Which Manage Users entry admins actually see: #manageUsersBtn is display:none with class 'replaced-by-status-bar' and #manageUsersBtnSidebar is hidden — does either ever become visible, or is User Settings the only real path (and what about the mobile burger)? → **Answered (walked + code).** The header #manageUsersBtn can NEVER appear: app.js sets `style.display=''` for admins, but the unconditional `.header .replaced-by-status-bar { display:none !important }` beats inline style (proven by forcing it in-page — computed display stays `none`). The real admin entries are the sidebar "Manage Users" button (`loggedIn && state.isAdmin`), which on ≤768px lives inside the drawer, and the three User Settings buttons (Add User / Manage User / All Users). The header button exists only as a dead click-dispatch target.
- Empty states: Manage Users with only yourself, a user with 0 projects clicking transfer/delete-reassign (are targets filtered?), #userProjectsModal for 0 projects, the Activity overview empty-timeline placeholder for a never-active user → **Partially answered (code).** `populateUserSelect` filters only the subject user out; with no other users the select renders a single disabled-ish "No other users" option (no other guard). Empty user list renders "No users". A 0-project count renders as plain text "0", not a link, so #userProjectsModal can't open empty from there. Live rendering walk-blocked.
- Error paths: creating a user with an existing email, password policy on Add User / Set Password, transfer with no other users, admin-delete-project failure — what do #adminCreateError / #deleteUserError / #transferError actually show? → **Partially answered (walked + code).** Client-side the ONLY rule is "Email and password required"; every other message is the server's `json.error` shown verbatim (fallbacks "Create failed" / "Transfer failed"), and a network failure surfaces the raw exception — verified live on the auth wall as "Failed to fetch". All Users adds a developer hint on Edge-Function failure: "Deploy: supabase functions deploy admin-list-users --no-verify-jwt". Real production texts (duplicate email, password policy) walk-blocked.
- Does Force turn-in interrupt the lock-holding editor in real time (toast/banner via the checkout subscription) or do they only find out on next save? → **Answered (code, live confirmation blocked).** There is no push to the holder. The holder's tab discovers the loss at the next checkout keepalive probe — `CHECKOUT_KEEPALIVE_MS = 10 minutes` on visible tabs — or at the next save/turn-in attempt, which routes into the recovery modal ("You no longer hold the checkout - refreshing." on the already-released branch).
- Does the per-project 'Force turn-in (admin)' in Project Settings appear only when someone else holds the checkout, and does the button row refresh after use (both there and in Manage Projects)? → **Answered (code).** `updateSettingsCheckoutSection` shows #settingsForceCheckIn only on the `state.checkedOutEmail && state.isAdmin` branch (someone else editing); every checkout action path calls it again, so the row refreshes. Manage Projects re-renders its list after `force_check_in_project`. Live click walk-blocked.
- Global force reload: exact prompt flow for the optional note, whether the pushing admin's own tab reloads, what a Dismissed banner tab does later, and whether session_start re-fires for each user after the forced reload (maybeLogSessionStartOnce scope) → **Mostly answered (code).** Flow: native `confirm("Force a hard reload on EVERY signed-in user … Continue?")` → native `prompt("Optional note shown to users (e.g. \"v1.42 update\"):")` → RPC → toast "Global reload triggered." The realtime subscription is not filtered by user, so the pushing admin's own tab gets the same banner and does NOT auto-reload. Dismiss (×) only sets `display:none` for that tab's lifetime; the reload still lands at next boot (`serverTs > localTs → doGlobalReloadNow('boot')`), and the stamp commits only after a confirmed reload so a blocked reload retries. session_start re-fire walk-blocked.
- Do All Users rows really expose the Activity overview (read-only claim vs the View activity button markup in features/user-admin.js lines 117/129)? → **Answered (code).** Yes — both lists compose the same `userActivityBtnHtml` cell and both call `wireUserActivityButtons`; All Users is "read-only" only in that it lacks the password/transfer/delete columns.

- How the wide Manage Users table (email, role, count, stacked dates, 4 action buttons) behaves on tablet/mobile widths → Walk-blocked (needs a session with real rows; the shells are plain flex rows with no responsive variant spotted in styles.css, so horizontal squeeze is likely — retest with a session).
- Timing: how long transfer-projects takes for a user with many projects (it moves storage objects too) and whether the UI shows progress → **Partially answered (code).** The confirm button flips to a busy "Transferring…" label and disables; there is no progress indication beyond that.
