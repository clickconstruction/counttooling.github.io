# T1-01 — Signed-out restore prompt + backup-clobber guard

**Plan of record for Tier-1 items #1 + #2 (JOURNEY-MAP.md "Ranked improvement shortlist",
rows 1–2). ONE PR — the two halves are inseparable: offering "Keep and Open" without the
clobber guard hands the user a poisoned restore.** Also carries J4's second half:
re-apply `pageCanvases` on same-PDF re-upload.

Sources of truth read for this plan: JOURNEY-MAP.md:185-201 (Tier-1 table),
journeys/save-load-return.md (J12, findings 1–2 + Verification), journeys/count-fixtures.md
(J4, finding 1 + Verification), journeys/field-tablet-offline.md (F1/F7), AGENTS.md, and the
code at every anchor below (re-read 2026-08-09 in this worktree; line numbers current).

## Problem (verified)

Signed out, closing and reopening the app loses all work even though a complete on-device
backup (marks + PDF blob) sits in IndexedDB: the "Project from Last Session" Keep/Discard
offer is gated inside the signed-in boot branch — `if (SUPABASE_ENABLED && supabase &&
state.supabaseSession?.user)` at **app.js:6470**, offer at **app.js:6486-6489** — while the
backup itself reads fine anonymously (`takeoffBackupGet('local', null)`, read at
**app.js:6434**). Worse, the unconditional 5-second interval at **app.js:5952**
(`setInterval(() => { writeTakeoffStateBackup(); }, 5000)`) overwrites the unrestored backup
~3.5–5.3s after boot with the near-empty new session (`{markers:0, pdfBlob:0}` — reproduced
three independent times), because the silent palette pre-apply at **app.js:6457** makes the
writer guard at **save-engine.js:264** pass; `idbTakeoffBackupPut` replaces the record
wholesale (**idb.js:219-221**) and the clobbering write's newer `lastModifiedAt` defeats
the stale-skip (**idb.js:200**). This also poisons the **signed-in** Keep: the Keep handler
re-reads the (now clobbered) record and prefers it by timestamp
(**features/restore-last-session.js:62-63** — `useIdbBackup = idbBackup &&
idbBackup.lastModifiedAt > projUpdated`), reproduced as a hard result: Keep after 9s
restored the PDF with **0 marks**. Third leg (J4 finding 1): re-uploading the *same* PDF
restores palette only, zero marks — `applyTakeoffBackupToState` runs at boot but its
`pageCanvases` writes target `state.pages[i]` which are empty pre-PDF
(**annotation-model.js:164-167**), and nothing re-applies them at PDF-open time (the
post-upload hash-match at **features/pdf-intake.js:248-277** is cloud-only).

Repro summary (adversarially verified, 0 of 9 findings killed): day 1 signed-out — upload
`samples/sample-plan.pdf`, counter + 3 marks → IDB `'local'` record holds
`{markers:3, pdfBlob:37,971B, projectName:'sample-plan'}`. Day 2 reopen — no prompt, palette
back at 0, backup destroyed by t+5.3s; re-upload same PDF → 0 marks. The restore machinery
itself is healthy: driving the real `openLastSessionRestorePrompt({proj, cachedBlob})`
against the real backup restored 1 page + 3/3 marks in **0.26s, fully offline, zero network**.

## Design

Mechanism chosen per the shortlist row: **key the boot backup aside until Keep/Discard**.
Explicitly NOT a "skip interval writes while `state.pages` is empty" guard — that variant
was rejected in J12 verification because it also drops backups of a counter palette built
*before* any PDF upload.

### 1. `constants.js` — held-key constant

Add `const TAKEOFF_BACKUP_HELD_ID = 'local-held';` next to the `TAKEOFF_BACKUP_*` block
(constants.js:118-132) and export it in the guarded CommonJS footer (constants.js:168-170
area) so tests can require it. This is an IDB record key in the existing
`takeoff_backup` store, not a new store — no IDB schema/version change.

### 2. `save-utils.js` — pure candidate picker

New pure function `pickBootRestoreCandidate(localEntry, heldEntry)`:
- an entry **qualifies for a prompt** when `entry && entry.data && entry.pdfBlob &&
  entry.pdfBlob.size > 0` (same predicate as today's `hasLocalPdf` at app.js:6485);
- returns `{ candidate, from }` where `from` is `'held' | 'local' | null`;
- prefer the held entry (it is a prior session's still-unresolved candidate); if **both**
  qualify, prefer the newer `lastModifiedAt` (a later working session outranks an ignored
  old prompt);
- if neither qualifies but one has `data`, return it with `promptable: false` so boot can
  still do the silent palette pre-apply and the J4 re-upload hook can find it.

Pure, no state — lives in save-utils.js with the other pure save helpers, unit-tested in
`save-utils.test.js` (node).

### 3. `app.js` boot (init IIFE, currently :6434-6506) — key-aside + hoisted offer

Rework the block in place:

```
const localEntry = await takeoffBackupGet('local', uid);
const heldEntry  = await takeoffBackupGet(TAKEOFF_BACKUP_HELD_ID, uid);
const { candidate, from, promptable } = pickBootRestoreCandidate(localEntry, heldEntry);
// KEY-ASIDE: before anything makes the writer guard pass, move a promptable
// 'local' candidate to the held key so no later write can destroy it.
if (promptable && from === 'local') {
  await takeoffBackupPut(TAKEOFF_BACKUP_HELD_ID, candidate.data, candidate.pdfBlob,
    candidate.pdfHash, candidate.lastModifiedAt, candidate.projectName, candidate.userId);
  await takeoffBackupDelete('local');
}
```

Ordering is the safety argument: until `applyTakeoffBackupToState` runs (currently
app.js:6457), state has no pages/counters/lineTypes, so the writer guard at
save-engine.js:264 skips every write — the key-aside completes before the dangerous window
opens. Keep the legacy localStorage `takeoff-state` migration (app.js:6436-6455) as-is,
feeding `backupToApply`; the silent palette pre-apply (app.js:6457) now applies
`candidate.data` (unchanged user experience: palette/groups/bindings/icons still return
silently).

Then **hoist the local offer out of the signed-in gate**. New shape:

```
let offeredRestore = false;
if (promptable) {
  const projForRestore = { id: 'local', name: candidate.projectName || 'Untitled',
    data: backupDataToProjFormat(candidate.data || {}), updated_at: null, pdf_path: null,
    pdf_hash: candidate.pdfHash, user_id: state.supabaseSession?.user?.id || null,
    checked_out_by: null, checked_out_at: null };
  App.openLastSessionRestorePrompt({ proj: projForRestore, cachedBlob: candidate.pdfBlob,
    heldBackup: candidate });
  logUserEvent('restore_prompt_shown', null, { source: 'local' });
  offeredRestore = true;
}
if (SUPABASE_ENABLED && supabase && state.supabaseSession?.user) {
  ... channels (unchanged, app.js:6472-6479) ...
  if (!offeredRestore) {
    ... cloudLast offer (unchanged, app.js:6491-6504) ...
    // + logUserEvent('restore_prompt_shown', last.projectId, { source: 'cloud' });
  }
}
```

The prompt copy ("You have a local session from your last visit: **name**") already reads
trade-plain — zero copy changes. Note `user_id` may now be null (signed-out); see §4 for
the isViewer consequence. There are no `await`s between the pre-apply and
`openLastSessionRestorePrompt`, so no interval tick can interleave (single-threaded
run-to-completion) — `pendingRestore` is set before any write becomes possible.

Also add to the localhost-only test-hook block (app.js:6323-6330):
`window.__takeoffBackupPutForTest = takeoffBackupPut;` and
`window.__writeTakeoffStateBackupForTest = writeTakeoffStateBackup;`.

### 4. `features/restore-last-session.js` — held record end-to-end + local editability

- `pendingRestore` now carries `heldBackup`. Register the getter-accessor (AGENTS.md
  pattern for feature-private state): `App.isRestorePromptPending = () => !!pendingRestore;`.
- `doRestoreLastProject(proj, cachedBlob)` → `doRestoreLastProject(proj, cachedBlob,
  heldBackup)`. When `heldBackup` is provided, **use it as `idbBackup` directly and skip
  the `takeoffBackupGet(proj.id, …)` re-read** (lines 62-63) — this kills the
  poisoned-Keep re-read for the local path outright (the local Keep handler at line 201
  clears `pendingRestore` *before* awaiting the restore, so the engine-side skip in §5
  stops protecting it mid-restore; the direct-use makes it immune). Cloud path keeps the
  existing re-read + timestamp preference (protected by §5 because the cloud Keep handler
  clears `pendingRestore` in its `finally`).
- **Local sessions have no checkout**: in the `proj.id === 'local'` branch, set
  `state.isViewer = false; state.canCheckOut = false;` after the existing derivation.
  Static read of lines 129-134 says today's local Keep computes
  `hasValidCheckout = (null === userId) && … = false` → `state.isViewer = true`, which
  would leave the restored session read-only AND silence future backups (the viewer guard
  at save-engine.js:263). **Verify at implementation time with a live drive before/after**
  — if signed-in local Keep already lands editable through some path this plan missed,
  keep the change anyway (it is then a no-op) but say so in the PR. The spec (below)
  pins post-Keep editability either way. Signed-out safety of the rest of the function:
  the local path touches no `App.getSupabase()` branch (only `pdf_path`-gated ones), and
  `refreshProjectPermissions` (save-engine.js:802) + `subscribeToProjectCheckoutChanges`
  early-return / no-op without a session or project id — same as the shipped local path.
- Local Keep success: `await takeoffBackupDelete(TAKEOFF_BACKUP_HELD_ID)` after
  `doRestoreLastProject` resolves (the restored state repopulates `'local'` on the next
  dirty/interval write). Log `restore_keep` (see Telemetry).
- Discard handler (lines 207-219): also `takeoffBackupDelete(TAKEOFF_BACKUP_HELD_ID)`.
  (`pdfCacheDelete(projectId)` + `takeoffBackupDelete(projectId)` stay.)
- Cloud Keep: log `restore_keep` with `source:'cloud'` on success.

### 5. `save-engine.js` — the clobber guard (pending-prompt hold)

In `writeTakeoffStateBackup` (save-engine.js:259-273), after the viewer guard:

```
if (ctx.isRestorePromptPending && ctx.isRestorePromptPending()) {
  backupClobberAvertedCount++;
  if (backupClobberAvertedCount === 1) {
    try { pushSaveEvent('backup_clobber_averted', 'Skipped backup write while the restore prompt is unresolved', ''); } catch (_) {}
  }
  try { saveDebugLog('backup_clobber_averted', { count: backupClobberAvertedCount }); } catch (_) {}
  return;
}
```

Wire `isRestorePromptPending: () => !!(window.App && App.isRestorePromptPending && App.isRestorePromptPending())`
into the `createSaveEngine(ctx)` context object in app.js (deferred lookup — the feature
file registers after app.js, per the registry load-order rule). Why this is safe and NOT
the rejected pages-empty skip: the prompt is a modal that blocks all editing, so a skipped
write can never lose new work; pre-PDF palette sessions (no prompt pending) back up
normally. This half is what protects the **cloud** candidate too — the
`clickcount-last-project` fallback inside `doWriteTakeoffBackupToIndexedDB`
(save-engine.js:300-324) otherwise re-keys the boot write onto the cloud project's own
backup record and poisons signed-in Keep the same way.

### 6. `features/pdf-intake.js` — J4's second half: re-apply marks on same-PDF re-upload

In `handleFreshUpload` (pdf-intake.js:283-367):

- Compute the upload hash once for everyone: `const uploadHash = hashBufForMatch ? await
  App.sha256Hex(hashBufForMatch) : null;` (today it's computed only inside the cloud-only
  `promptLoadAnnotations`/`matchPendingCanvasLoad`; pass it down to avoid double hashing).
  Stash `App.state.localPdfHash = uploadHash;` — a **new in-memory-only state field** (do
  NOT reuse `state.pdfHash`, which carries cloud-PDF semantics through the save/upload
  ladder).
- In `doWriteTakeoffBackupToIndexedDB` (save-engine.js:351): `const pdfHash =
  state.pdfHash || state.localPdfHash || null;` — signed-out backups now carry a
  verifiable hash, which is what makes the re-apply below (and any future match) safe.
- New helper `maybeReapplyLocalBackupMarks(uploadHash)` called near the end of
  `handleFreshUpload` (after pages + `state.currentPage` are set, before the cloud
  `promptLoadAnnotations` branch at :361). Gates — ALL must hold:
  - `!App.state.supabaseSession?.user` (signed-out only; signed-in keeps the existing
    cloud hash-match flow untouched),
  - `!App.state.pendingCanvasLoad && !App.state.currentProjectId`,
  - current pages have no annotations (`!App.projectHasAnyCanvasMarkup()` — publish it on
    the registry if not already there),
  - a candidate record exists (held key first, then `'local'`) whose `data.pageCanvases`
    contains at least one mark,
  - **hash-verified same PDF**: `candidate.pdfHash === uploadHash`, or, when
    `candidate.pdfHash` is null but `candidate.pdfBlob` exists, hash the blob via
    `App.sha256Hex(await blob.arrayBuffer())` and compare. No hash → no apply (never put
    marks on an unverified PDF; this is a Tier-1 data-trust item).
  - On match: `App.applyTakeoffBackupToState(candidate.data)` (pages now exist, so
    `pageCanvases`/`pageScales`/`pageRotations`/`pageBakeFrames` all land, including the
    existing `verifyPageBakeFrame` warn path), `App.clearUndoStacks()`,
    `App.markProjectDirty()`, delete the candidate record (held and/or `'local'`),
    `App.updateUI(); App.renderPdf();`, and toast:
    `App.showToast('Restored your marks from the last session.', 5000)`.

Why this half still matters once the prompt exists: the prompt is only offered when the
backup carries the PDF blob; a data-only backup (blob missing — e.g. `state.pdfBuffer`
detached by pdf.js, `byteLength` 0, see AGENTS.md `state.pdfBufferSize` note) silently
skips the prompt today and forever. The hash-stamped backup + re-upload hook closes that
gap.

### What does NOT change

- Prompt copy, modal markup (`#lastSessionRestoreModal`), Keep/Discard button labels.
- The Esc ladder (app.js:5775+) — `lastSessionRestoreModal` stays off it (Tier-3 B1).
- The hardcoded `'document.pdf'` restore label (restore-last-session.js:102-103) — Tier-3
  B6 owns that one-liner; expect merge adjacency, don't fix it here.
- `takeoffBackupGet` user-mismatch semantics (save-engine.js:226-235) — unchanged.
- The 1s debounce / 5s interval cadence; the silent palette pre-apply at boot.
- Export Canvas / Import Canvas; the signed-in cloud offer ordering (local beats cloud,
  as today).
- No new UI surface anywhere — the entire change reuses the existing modal and toasts.

### Simplicity budget

Removes: the signed-out export-to-file ritual; the re-upload dead end and the recount it
forces; the 5-second self-destruct race (a whole class of "the app lost my work" support
incidents); the need for guides to caveat "signed-in only" on the restore story —
`how-your-work-is-saved.md` becomes truthful with a one-line edit instead of a rewrite.
Adds: one IDB record key, one pure picker function, one guard clause, one intake hook. No
new modal, no new setting, no new dependency.

## Risks & edge cases

- **isViewer after local Keep** (the plan's one "verify live" item): static read says the
  shipped local Keep lands `state.isViewer = true` (restore-last-session.js:131-134),
  which would both block editing and silence backups (save-engine.js:263). The fix in §4
  is required for signed-out restores regardless; drive the signed-in local path
  before/after and record what actually happens in the PR.
- **Shared machine**: an anonymous boot can now be offered a signed-in user's un-saved
  `'local'` backup (`takeoffBackupGet` only deletes on mismatch when BOTH user ids are
  truthy, save-engine.js:229). This is pre-existing device-local data (and the inverse
  case is J12 open question :162); the prompt adds visibility, not access. Keep semantics
  unchanged; flag as a product note for Will.
- **LRU eviction of the held record**: `TAKEOFF_BACKUP_MAX_ENTRIES = 5`
  (constants.js:131); the eviction loop in `idbTakeoffBackupPut` (idb.js:211-218) evicts
  by oldest `lastUsed` and only skips the record being written. The key-aside put stamps a
  fresh `lastUsed`, so eviction would need 5 newer *other* records in one anonymous
  session — implausible but real; acceptable for this PR, noted for a follow-up
  (exempting the held key from eviction is a 2-line idb.js change if it ever bites).
- **Supabase disabled** (`SUPABASE_ENABLED` false): the hoisted offer and local Keep must
  run clean — AGENTS.md hard rule. The local path dereferences no supabase client
  (verified: only `pdf_path`-gated branches do); add it to the spec run (the Playwright
  server runs with the stub config; the extended spec exercises exactly this).
- **Cloud Keep during fetch**: `pendingRestore` stays set until the `finally` block, so
  the §5 hold covers the whole "Loading…" window including `doRestoreLastProject`'s
  re-read. Local Keep clears `pendingRestore` before awaiting — immune via the
  `heldBackup` direct-use instead (§4). Both halves are needed; neither alone is correct.
- **Prompt ignored forever**: the held record persists across reloads by design (that IS
  the fix for the ignore-then-reload loss). It is bounded: one record, consumed on
  Keep/Discard, evictable under the LRU byte cap.
- **Legacy localStorage migration path** (app.js:6436-6453) writes `'local'` during boot —
  runs only when the IDB record is absent, so it cannot collide with a qualifying
  candidate; the picker sees its result on the *next* boot. No change needed.
- **Interactions with other Tier-1 items**: #12 (dead view-link, app.js:6391) edits the
  same init function — coordinate merges if parallel. #8 (T1-08 append-rename guard) edits
  the same `handleFreshUpload` in features/pdf-intake.js (guard at :344-348 + toast after
  :350) that §6 hooks, and also extends pdf-upload.spec.js — interleaved hunks; whichever
  branch lands second re-verifies anchors and rebases. Tier-3 B1 will later add
  `lastSessionRestoreModal` to the Esc ladder — fine; Esc-closes-prompt must then behave
  like neither Keep nor Discard (pendingRestore kept? decide in B1 — with this PR's hold,
  an Esc-dismissed prompt would suspend backups for the session, so B1 MUST route Esc to
  the Discard-or-reopen semantics, not a bare hide; leave a code comment saying so).
- **`restore_prompt_shown` volume**: fires at most once per boot; no throttle needed
  (unlike the high-frequency events at app.js:2744-2749).

## Acceptance criteria

A reviewer can walk these end-to-end (all signed-out unless stated; local static server,
fresh profile):

1. Upload a PDF, place 3 counter marks, close the browser. Reopen: the "Project from Last
   Session" prompt appears with the project name. **Keep and Open** restores the PDF and
   all 3 marks, offline, with zero network requests.
2. After Keep, the session is editable (place a 4th mark) and a new `'local'` IndexedDB
   backup containing 4 marks lands within ~6s.
3. Reopen and *wait 10+ seconds* before clicking Keep: all marks still restore (the
   clobber race is dead); the Save Status log shows `backup_clobber_averted`.
4. Reopen and close again without answering the prompt, twice: the prompt still appears
   with all marks intact on every boot.
5. **Discard** deletes the held and `'local'` records; the next boot shows no prompt.
6. With a data-only backup (no PDF blob) carrying a matching `pdfHash`: no prompt at boot,
   but re-uploading the *same* PDF re-applies every mark with a toast; uploading a
   *different* PDF applies nothing.
