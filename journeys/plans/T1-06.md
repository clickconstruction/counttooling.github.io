# T1-06 — Arc length FP-drift fix (arc >= chord)

> Plan of record for Tier-1 shortlist item #6 (JOURNEY-MAP.md, "Ranked improvement
> shortlist", row 6). Source dossier: journeys/measure-runs.md (J5), friction #1
> (blocker, CONFIRMED). This plan is self-contained: a fresh session can execute
> it without reading the journey program docs.

## Problem (verified)

Curved ("arc") line types under-measure every run by ~4–5%: identical click
pairs through the armed Line tool read **Straight 15.30 ft but Arc 14.73 ft** —
an arc measuring *shorter than its own straight chord*, which is geometrically
impossible. Root cause is `quadraticBezierLength` in **geometry.js:91-99**: the
sampling loop walks `for (let t = 0.05; t <= 1; t += 0.05)` and floating-point
drift makes the accumulated t reach `0.9500000000000003`, then the next
increment (`1.0000000000000004`) fails `t <= 1` — so the final segment of every
curve (from t≈0.95 to the endpoint) is never summed. Verified numerically in the
dossier (journeys/measure-runs.md:109, 173): for a 100-unit chord with the app's
fixed 15% bow, the shipped code returns **96.28** where the true arc length is
**101.48** (−5.1%). The call chain to user-visible totals is confirmed:
`line-metrics.js:24-31` (`lineSegmentLength` routes `curveStyle === 'arc'`
through `getQuadraticBezierControlPoint` + `quadraticBezierLength`) →
`lineLengthPdfPts` / `lineRealWorldLength` / `lineLengthForTotals` → the app.js
same-named wrappers (`quickLineLength`, `getLineLengthForTotals`, …) → sidebar
Lines totals, canvas length labels, report/summary/export footage. The shortage
is silent, looks authoritative, and compounds across a bid.

The sibling function `distToQuadraticBezier` (**geometry.js:100-109**) contains
the *same* buggy `t <= 1` float loop but is accidentally saved by its final
`Math.min(minD, ptDist(pos, p2))` clamp (dossier line 187) — hit-testing is
correct today. It must be commented so the broken loop pattern isn't copied
again, but its behavior must not change.

**Data caveat:** stored annotations hold endpoints only; lengths are computed
live on every render/report. No migration — existing projects simply start
reading the corrected (~5% longer) arc footage after deploy.

## Design

### geometry.js — the one behavioral change

Replace the float-accumulator loop in `quadraticBezierLength` (currently
geometry.js:91-99) with an integer-step loop that lands on `t = 1` exactly:

```js
  // 20-step polyline approximation of the curve. Integer loop so the final
  // step lands on t = 1 exactly — a float `t += 0.05` accumulator drifts to
  // 1.0000000000000004 and drops the last segment (~5% short on every arc).
  function quadraticBezierLength(p0, p1, p2) {
    const STEPS = 20;
    let len = 0, prev = p0;
    for (let i = 1; i <= STEPS; i++) {
      const pt = quadraticBezierPoint(i / STEPS, p0, p1, p2);
      len += ptDist(prev, pt);
      prev = pt;
    }
    return len;
  }
```

Note `quadraticBezierPoint(1, p0, p1, p2)` evaluates to exactly `p2`
(`(1-t)` terms vanish), so the polyline now terminates on the true endpoint and
`arc >= chord` holds by the triangle inequality — no epsilon needed.

### geometry.js — comment-only change on the twin

Add a comment to `distToQuadraticBezier` (currently geometry.js:100-109), on or
above its `for (let t = 0.05; t <= 1; t += 0.05)` line, e.g.:

```js
    // NOTE: this float t-loop drops its final step to the same FP drift that
    // broke quadraticBezierLength (fixed there with an integer loop) — but
    // here the trailing Math.min(minD, ptDist(pos, p2)) clamp closes the gap,
    // so hit-testing is correct. Don't copy this loop shape into new code.
```

Do **not** rewrite its loop. Its behavior (and therefore canvas hit-testing at
app.js:1026) stays byte-identical.

### geometry.test.js — fix the stale lock-in comment

The existing `'quadratic bezier helpers'` test (geometry.test.js:81-94)
deliberately locked the buggy behavior with the comment "*slightly undershoots
due to the float t-loop dropping the final step*" and tolerance `0.6`
(line 85-87). After the fix the collinear case returns exactly 10; update the
comment and tighten: `close(g.quadraticBezierLength(p0, p1, p2), 10, 1e-9)`.
New assertions go in a new test (see Tests).

### What does NOT change

- `distToQuadraticBezier` behavior (comment only) — hit-testing untouched.
- `lineSegmentLength` / all of line-metrics.js — it already delegates; the fix
  flows through automatically.
- The app.js wrappers and every `window.*` global consumed by report.js
  (`quickLineLength`, `getLineLengthPdfPts`, `getLineLengthForTotals`, …) —
  signatures and names frozen per AGENTS.md.
- Arc *drawing* — rendering uses `quadraticBezierPoint` / canvas bezier calls,
  not the length function. Curve pixels are identical; only the length-label
  *text* on arc lines changes (see render-pixels note below).
- Stored data / save-load / export-import — nothing persisted changes shape.
- No `App` registry changes, no new files, no app/index.html changes.

### Simplicity budget

Removes the standing reason to distrust/avoid Curved line types (dossier
proposal, measure-runs.md:122 — spiritPass yes), removes a stale
excuse-the-bug comment in geometry.test.js, and inoculates the codebase against
re-propagating the float-accumulator loop via the twin comment. Net new code:
~2 lines (constant + comment); no new concepts, files, or settings.

## Tests

House naming (AGENTS.md / playwright.config.js `testMatch`): `*.test.js` =
Node unit tests (`npm run test:unit`), `*.spec.js` = Playwright. geometry.test.js
owns this surface — extend it; no new files.

1. **geometry.test.js** — new test
   `'quadraticBezierLength: includes the final step — arc >= chord'`:
   - Degenerate/straight: collinear control → length exactly the chord
     (`close(..., 10, 1e-9)`, replacing the loose 0.6 tolerance; fold into the
     existing test as described above).
   - The app's real geometry: `p0 = {x:0,y:0}`, `p2 = {x:100,y:0}`,
     `ctrl = g.getQuadraticBezierControlPoint(p0, p2, 1)` (the fixed 15% bow,
     geometry.js:80-87) → assert
     `g.quadraticBezierLength(p0, ctrl, p2) >= g.ptDist(p0, p2)` (strict
     `>` in fact), and `close(len, 101.48, 0.05)` — the dossier's independently
     computed true arc length for this bow (measure-runs.md:173). This pins the
     regression: the shipped bug returns 96.28 here and fails loudly.
   - Endpoint containment: last sampled point is `p2` → adding
     `ptDist(lastSample, p2)` can't be simulated directly, so instead assert
     symmetry: `quadraticBezierLength(p0, ctrl, p2)` equals
     `quadraticBezierLength(p2, ctrl, p0)` within 1e-9 (the buggy version is
     asymmetric only in which end it truncates — cheap invariant, keep it).
2. **line-metrics.test.js** — strengthen the existing arc test at
   line-metrics.test.js:21-27 (`'lineSegmentLength: arc line type routes to the
   bezier path (differs from chord)'`): replace/augment
   `assert.notStrictEqual(arc, chord, …)` with `assert.ok(arc > chord, 'an arc
   is longer than its chord')`. This guards the integration seam (curveStyle
   routing + control-point + length together).
3. **Playwright** — no new spec. The behavior is pure math with the node tests
   as the guard (per the shortlist row). But **render-pixels.spec.js** baselines
   WILL change: its fixture includes arc quick lines *with length labels*
   (ARCHITECTURE.md row, render-pixels.spec.js), and the label text now shows
   the corrected length. Regenerate on the baseline machine:
   `npx playwright test render-pixels.spec.js --update-snapshots` and commit the
   changed snapshots in `render-pixels.spec.js-snapshots/`. (Baselines are
   darwin-rasterized and CI-ignored — regenerate locally, eyeball the diff is
   label-text-only.)
4. Manual repro walk (from the dossier): same two clicks through a Straight
   type then an Arc type — Straight 15.30 ft, Arc must now read ~15.53 ft
   (chord × ~1.0148), never less than the straight reading.

## Risks & edge cases

- **All existing curved runs read ~5% longer after deploy.** Correct, but a
  user who priced a bid off the old number may notice totals grow with no UI
  change. This is the fix working; if it surfaces as a support question the
  answer is "arc lengths were under-measured ~5%; corrected". No migration or
  banner — lengths were never persisted.
- **render-pixels.spec.js baseline churn** — the length-label text on arc
  fixtures changes. If baselines are regenerated on a different machine than
  the committed ones, *every* snapshot changes (font rasterization), muddying
  the diff. Regenerate on the same machine that produced the current baselines
  or accept a full-set regen in a clearly labeled commit.
- **Tier-1 interaction — item #7 (zone presets skip sheet correction,
  features/scale.js)**: both items shift measured/real lengths. Land them in
  separate branches with separate baseline/spec updates so a totals change is
  attributable to exactly one fix; if #7 lands first and added specs with
  hard-coded arc footage, those expectations must be re-derived here (and vice
  versa).
- **Tier-1 interaction — item #8/#9**: none (project naming / palette load —
  disjoint surfaces).
- **Do not "fix" `distToQuadraticBezier`'s loop while in there.** Its clamp
  makes it correct; changing its sampling would perturb hit-test distances near
  the tolerance boundary for zero benefit and would invalidate the "comment,
  don't rewrite" decision recorded in the dossier (measure-runs.md:187).
- **Line-number drift**: geometry.js anchors (91-99, 100-109) verified
  2026-08-10 on branch `claude/app-review-e1c130`; re-grep
  `quadraticBezierLength` before editing (AGENTS.md: don't trust line numbers).
- Report.js contract: untouched wrappers keep their `window.*` names — run a
  quick grep to confirm no signature drift (`quickLineLength`,
  `getLineLengthForTotals`) if any refactor temptation creeps in. It shouldn't.
