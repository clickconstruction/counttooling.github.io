# T1-08 — Append-upload never renames the open project

> Plan of record for Tier-1 item #8 (JOURNEY-MAP.md "Ranked improvement shortlist", Tier 1 row 8).
> Source dossier: journeys/trim-and-organize-a-bid-set.md (J2), friction #1 (blocker, CONFIRMED)
> and friction #8 (papercut, CONFIRMED — silent append). Self-contained: everything needed to
> execute is restated here; line anchors verified against the working tree on 2026-08-10.

## Problem (verified)

Uploading an addendum PDF while a project is open silently renames the project to the new
file's name. The rename is the unconditional `else` branch in `handleFreshUpload`
(**features/pdf-intake.js:344-348** — the assignment is line 347:
`App.state.currentProjectName = titleFromPdfFilename(filesToProcess[0].name);`), which runs on
every upload that isn't a pending-canvas-load match — including when pages are already loaded
(`startPageIdx > 0`, captured at features/pdf-intake.js:284) and **even when
`state.currentProjectId` is set** (an open cloud project; reproduced in the J2 adversarial
re-drive with a stubbed id). The same code path calls `App.markProjectDirty()`
(features/pdf-intake.js:342), and `performAutoSave` reads the name at **save-engine.js:2469**
(`const name = ctx.getState().currentProjectName || 'Untitled';`) — so for a signed-in user
the wrong name reaches the cloud row via autosave within ~5s, with no manual save at all.
The code already knows this is wrong: the comment at **features/pdf-intake.js:357-360** (guarding
the prompt gate at :361) says the prompts on this path "would either offer to switch projects
(destructive) or **clobber the project name**" — but the guard suppresses only the prompts,
not the line-347 rename.

Repro (from the dossier, walked + independently re-driven on port 4302, signed-out headless
Chromium): open 'Riverside Clinic Plumbing' (test-2pages.pdf renamed), click Upload PDF, pick
test-page.pdf → pages append correctly but the status bar reads 'test-page'
(journeys/img/trim-and-organize-a-bid-set-07.png). The guide
(content/guides/preparing-a-plan-set.md:29) explicitly tells users to do exactly this. A
sibling papercut (J2 friction #8, also CONFIRMED): the append gives no feedback at all — no
"Added N sheets" toast exists anywhere in the intake path.

Not the bug: the Prepare-PDF append route (Project Settings > 'Add additional PDF pages' →
`handleAppendPages` → `openPreparePdfModal(..., { mode: 'append' })`) already locks the name —
features/prepare-pdf.js:239-241 reuses `App.state.currentProjectName` in append mode and :113
hides the project-name editor. Only the plain Upload-PDF-again path
(`handleFreshUpload`) renames; the dispatcher (features/pdf-intake.js:370-388) routes there
whenever the `pendingAddAdditionalPages` flag is unset.

## Design

### features/pdf-intake.js — the one-line guard + the toast

**1. Guard the rename (the fix).** In `handleFreshUpload`, replace the `else` branch at
:344-348 so the filename→name assignment only happens on a genuinely fresh upload:

```js
if (App.state.pendingCanvasLoad && firstBuf) {
  await matchPendingCanvasLoad(filesToProcess, firstBuf);
} else if (startPageIdx === 0 && !App.state.currentProjectId) {
  // Fresh upload into an empty session: name the project after the first file.
  // Appending to loaded pages (startPageIdx > 0) or an open cloud project must
  // NEVER clobber the name — see the guard comment below (:357-360) and J2/T1-08.
  App.state.currentProjectName = titleFromPdfFilename(filesToProcess[0].name);
}
```

`startPageIdx === 0` covers the walked signed-out repro (pages loaded, no project id);
`!App.state.currentProjectId` covers the verified worse case (open cloud project, e.g. a
canvas-only project whose pages arrive by another route). The decline branch inside
`matchPendingCanvasLoad` (features/pdf-intake.js:117) still renames — that path deliberately
drops the project, so the rename is correct there. Do not touch it.

**2. Append feedback (the toast).** In `handleFreshUpload`, after the merge succeeded and
`App.updateUI()` ran (i.e. after :350, before the prompt gate), when `startPageIdx > 0`:

```js
if (startPageIdx > 0) {
  const added = App.state.pages.length - startPageIdx;
  App.showToast('Added ' + added + ' sheet' + (added === 1 ? '' : 's') + ' to ' +
    (App.state.currentProjectName || 'Untitled'), 3500);
}
```

Trade words per the proposal: "sheets", and it names the job. `App.showToast` is registered
(app.js:2607 `showToast` → `airboardToastModal` / `#airboardToastText`; published on the App
registry). Place it after the size-cap early-returns so a rolled-back merge never toasts.

**3. Parity toast on the Prepare-append commit (cheap, same topic).** The Project-Settings
append route is equally silent after commit. Extend `commitPreparePdfToState`'s append return
(features/prepare-pdf.js:314) to `{ ok: true, name, pdfBuffer: App.state.pdfBuffer, appended:
true, appendedCount: kept.length }`, and in the `#preparePdfDone` onclick (features/prepare-pdf.js:351-359)
show the same toast when `r.appended`. This closes the Tier-3 B2 batch line
"'Added N sheets' append toast (J2)" — note that in the PR description so B2 doesn't re-ship it.

### What does NOT change

- `handleAppendPages`, the dispatcher, `titleFromPdfFilename`, `matchPendingCanvasLoad`
  (including its decline-path rename), `promptLoadAnnotations`, and the prompt gate at :361.
- Prepare-PDF fresh-mode naming (features/prepare-pdf.js:338) — unchanged.
- save-engine.js — unchanged; it was only ever the victim (it faithfully pushes whatever
  `currentProjectName` holds).
- No new setting, no new persisted field, no export/import change, no modal/HTML change.

### Simplicity budget

Removes an entire failure mode (silent wrong-name cloud pushes) and the need to document it;
removes the "no feedback on append → user uploads twice" guesswork (J2 friction #8); makes the
guide sentence at preparing-a-plan-set.md:29 truthful instead of aspirational. Net new code:
~10 lines, zero new UI surfaces. This is a bug fix the code's own comment already argued for.

## Risks & edge cases

- **Intentional new-project-by-upload is gone for loaded sessions.** A signed-out user who
  uploads a second PDF *wanting* a fresh project now keeps the old name. That is the designed
  append semantics (dossier proposal, spiritPass true); starting over = reload / close project.
  Watch for feedback, but do not add a prompt (the :357-360 comment forbids prompts here).
- **Decline path must keep renaming** (features/pdf-intake.js:117) — it drops the project, so
  filename-naming is correct there. The guard must not be hoisted above `matchPendingCanvasLoad`.
- **Toast is currently a full-screen click-swallowing overlay** (Tier-2 #15,
  styles.css:475): this adds one more 3.5s blocking toast right after an append. Accepted for
  now; T2-15's non-blocking-corner rework will inherit it automatically. Keep the spec
  assertion on `#airboardToastText` content, not styling/position, so T2-15 doesn't break it.
- **Interaction with T1-01/T1-02 (backup/restore):** the IndexedDB takeoff backup written
  after intake now carries the correct name — strictly an improvement. BUT coordination IS
  needed at the file level: T1-01 §6 edits the same `handleFreshUpload` (upload-hash stash +
  a signed-out re-apply hook placed after :350, before the prompt gate at :361 — the exact
  region this plan's guard at :344-348 and toast after :350 sit in) and also extends
  pdf-upload.spec.js with a new describe block. Whichever branch lands second must re-verify
  these anchors and rebase its interleaved hunks; the edits are logically independent.
- **Interaction with Tier-3 B2** (pdf-intake feedback batch): the append toast line lands
  here; B2 retains the corrupt-PDF fresh-path message and import toasts. Say so in the PR.
- **Interaction with T2-26** (thumbnail-grid trim): rebuilds Prepare PDF's innards but not
  `handleFreshUpload`; the guard is orthogonal. The `appendedCount` return field should
  survive that rework.
- **Merge-cap rollback:** the 50 MB post-merge rollback (features/pdf-intake.js:317-329)
  returns before the toast site — verify the toast cannot fire on "No pages were added."
- `state.currentPage = startPageIdx` (:349) already jumps the view to the first new sheet;
  with the toast this is the complete feedback story — don't add more chrome.
