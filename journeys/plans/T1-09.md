# T1-09 — Load-from-Cloud re-links marks instead of orphaning

Plan of record for Tier-1 shortlist item #9 (JOURNEY-MAP.md "Ranked improvement
shortlist", row 9). Source dossier: `journeys/reuse-standards-across-bids.md`
(friction finding #1, blocker; rework proposal #1; adversarial verification
2026-08-02). Line anchors below verified against the working tree on 2026-08-10 —
re-verify with grep before editing; app.js especially drifts.

## Problem (verified)

Mid-bid "Load from Cloud" (User Settings → Artboard) wholesale-replaces the open
project's palette: `features/my-settings.js:65-87` assigns `state.counters` /
`state.lineTypes` (and icon names/order, custom icons, modifiers, Quick Key
bindings with `replace: true`) straight from the fetched cloud artboard, with **no
undo snapshot pushed and no reconcile pass**. Placed marks are keyed by palette id
(`ann.counterMarkers[counterId]`, `quickLine.lineTypeId`, `polyline.lineTypeId`),
so when the cloud artboard carries the same trade names under different ids, all
placed marks stay drawn (canvas-draw.js:483-486 renders orphaned ids with a
fallback yellow circle — they keep *looking* counted) but drop out of
sidebar/Summary/legend: every tally reads 0. Reproduced independently (stubbed
cloud, 14 seeded marks): sidebar read "Water Closet 0 / Lavatory 0", all 14
markers present under orphaned ids, the undo button DISABLED after load, Ctrl+Z
restored nothing. The repair helper `reconcileOrphanedCountersAndLineTypes`
(annotation-model.js:254-296) already runs on **6 other intake paths** — sign-in
restore (features/restore-last-session.js:113), load-project
(features/load-project.js:444, :490), pdf-intake ×2 (features/pdf-intake.js:142,
:228), canvas-repair (features/canvas-repair.js:85), copy-project
(features/copy-project.js:156), import-clear (features/import-clear.js:70) —
Load-from-Cloud is the odd one out. An estimator who taps this button mid-takeoff
silently loses the count they are being paid for.

## Design

### 1. `annotation-model.js` — new relink pair (the only new logic)

Add two functions to the `createAnnotationModel(ctx)` factory and its return
object (annotation-model.js:503 export list), following the file's existing
style. Do **not** change `reconcileOrphanedCountersAndLineTypes` itself — its 6
existing call sites keep byte-identical behavior; name-matching lives only in the
new pair.

- `planPaletteRelink(incomingCounters, incomingLineTypes)` → returns
  `{ counterIdMap, lineTypeIdMap, relinkedMarks, orphanedMarks }`.
  - Name key rule: `String(s || '').trim().toLowerCase()` — the exact convention
    Palette Insights already uses for its "✓ On Artboard" badge
    (features/palette-insights.js:36 `nameKey`).
  - For each *current* `state.counters[i]` / `state.lineTypes[i]` whose nameKey
    matches an incoming item's nameKey, map oldId → newId (first incoming match
    wins on duplicate names — deterministic). Identity mappings (oldId === newId)
    are dropped from the maps.
  - Walk `state.pages[].canvases[].annotations` (via the factory's own
    `getPageCanvases`) counting placed marks: markers under a mapped counter id
    and quickLines/polylines with a mapped lineTypeId → `relinkedMarks`; marks
    referencing a current-palette id with **no** name match in the incoming set →
    `orphanedMarks`. (Marks already orphaned before the load count toward
    neither; reconcile's Unknown backfill still covers them.)
- `applyPaletteRelink({ counterIdMap, lineTypeIdMap })` → rewrites annotations in
  place across every page/canvas: renames `ann.counterMarkers[oldId]` keys to the
  mapped new id, **merging** (concatenating arrays) when the target key already
  exists — two old counters can name-match one incoming counter; rewrites
  `quickLine.lineTypeId` and `polyline.lineTypeId` through `lineTypeIdMap`.
  Returns nothing. No UI calls — the caller renders.

app.js: same-named thin wrappers + registry publishes, mirroring the reconcile
precedent exactly (wrapper at app.js:156, publish at app.js:6105):
`function planPaletteRelink(...a) { return annotationModel.planPaletteRelink(...a); }`
etc., then `App.planPaletteRelink = planPaletteRelink;` /
`App.applyPaletteRelink = applyPaletteRelink;` in the
`// SECTION: App feature registry` block. (Do not trust line numbers in app.js —
navigate by the SECTION markers.)

### 2. `features/my-settings.js` — rework the `#mySettingsLoadAirboard` handler (:65-87)

New flow (order matters — fetch must precede confirm so the warning can state
real numbers):

1. `const data = await App.fetchUserAirboard();` — the existing
   "No saved artboard found" toast path (:71-74) is unchanged, just moved ahead
   of the confirm.
2. `const plan = App.planPaletteRelink(data.counters || [], data.lineTypes || []);`
3. Confirm (still `confirm()` — feedback-channel unification is dossier papercut
   #8, out of scope here):
   - Palette empty and no placed marks → no confirm, as today (:67 guard).
   - Palette non-empty, **zero placed marks** → keep today's copy: `Replace your
     current artboard with the saved version from the cloud?`
   - Placed marks exist (`relinkedMarks + orphanedMarks > 0`) → trade-terms copy,
     e.g.: `Load your saved Artboard from the cloud? Your 14 placed marks stay
     on the sheet — 12 match by name and keep counting under the loaded
     counters and lines.` plus, when `orphanedMarks > 0`: ` 2 marks don't match
     anything in the saved Artboard — they'll keep counting under an "Unknown"
     row.` ending with: ` Undo brings your current counters, lines, and counts
     back.` (Per the dossier's Clear-copy amendment: do NOT promise Quick Key
     bindings come back — undo-stack.js snapshots omit `numberKeyBindings` and
     modifier prefs.)
4. `App.pushUndoSnapshot();` — before any mutation. (undo-stack.js `pushUndoSnapshot`
   no-ops when `!state.pages.length` — fine: with no pages there are no marks to
   orphan, and the palette-only replace was already the confirmed intent.)
5. Existing palette apply block (:75-83) unchanged — counters, lineTypes,
   iconNames, iconOrder, customIconPaths, modifiers, `seedQuickKeysFromArtboard`
   with `replace: true`.
6. `App.applyPaletteRelink(plan);` then `App.reconcileOrphanedCountersAndLineTypes();`
   — the reconcile is the backstop: any mark still orphaned (no name match)
   becomes a visible "Unknown" row (yellow circle / blue line) so no tally ever
   silently reads 0. This makes Load-from-Cloud the 7th intake path on the
   helper, closing the odd-one-out.
7. `if (App.state.pages.length) App.markProjectDirty();` — the relink mutated
   annotations, and the loaded palette itself is per-project persisted state;
   today's handler never dirties, so a loaded palette isn't even autosaved.
   (Clear already calls it, :112.)
8. Existing `App.updateUI(); App.renderAnnotations();` + success toast (:84-86)
   unchanged.
9. `App.logUserEvent('artboard_load', App.state.counters && App.state ?
   (App.state.currentProjectId || null) : null, { relinkedMarks: plan.relinkedMarks,
   orphanedMarks: plan.orphanedMarks, counters: (data.counters || []).length,
   lineTypes: (data.lineTypes || []).length });` — see Telemetry.

Update the my-settings.js header comment (its file-contract paragraph) to name
the new deps: `App.planPaletteRelink`, `App.applyPaletteRelink`,
`App.reconcileOrphanedCountersAndLineTypes`, `App.pushUndoSnapshot`,
`App.markProjectDirty`, `App.logUserEvent`.

### 3. Supabase migration — `artboard_load` must be allow-listed

`log_user_event` raises `invalid event type` for anything outside its hardcoded

session_start, project_open, project_save, export_pdf, export_canvas,

never records. Add `supabase/migrations/<timestamp>_log_user_event_allow_artboard_load.sql`
re-creating `public.log_user_event` with `'artboard_load'` added to the `in (...)`
list (copy the LATEST deployed function body — earlier Phase-4 branches may already have
re-created it with their own event types, e.g. restore/scale events; building on the
original 20260326230000 body would silently break theirs. Keep security definer,
search_path, grants as-is — the 2026-07-24 revokes are separate statements and stand). Apply via the
Supabase MCP `apply_migration` tool per AGENTS.md (name = filename without .sql).
Note in passing (do NOT fold in): app.js:1522 already logs
`render_worker_fallback`, which is also absent from the allow-list and therefore
dropped server-side — flag as a separate follow-up, not this branch.

### What does NOT change

- `reconcileOrphanedCountersAndLineTypes` internals and its 6 existing call sites.
- `fetchUserAirboard` / `saveUserAirboard` engine (app.js), Save / Export / Clear
  handlers in my-settings.js.
- `seedQuickKeysFromArtboard(..., { replace: true })` semantics — explicit load
  still replaces bindings (the user confirmed "replace").
- Sign-in auto-restore (fill-if-empty) path.
- The undo-stack snapshot shape (bindings/modifiers stay un-snapshotted; the
  confirm copy is written so it doesn't over-promise).
- `confirm()` as the channel.

### Simplicity budget

Removes the entire "palette-id internals" concept from the user's world: marks
either keep counting under matched names or surface as a visible "Unknown" row —
the silent zero-tally failure class is deleted. No new UI surface, no new modal,
no new persisted setting. Reuses three existing mechanisms (nameKey rule,
pushUndoSnapshot, reconcile) instead of inventing parallel ones; the guide's
"start a new bid with my standards" claim becomes true mid-bid as well.

## Risks & edge cases

- **Duplicate names in either palette** — first-match-wins must be deterministic
  and covered by a unit test; merging marker arrays on key collision must never
  drop markers. This interacts with the known carry-over duplicate-stacking harm
  (dossier finding #5: "Water Closet" twice in the sidebar) — two same-named old
  counters will both relink to one incoming counter and their tallies merge;
  that is the correct trade-terms outcome (one "Water Closet" row counting all
  of them) but call it out in the PR description.
- **Undo blind spot** — pushUndoSnapshot omits `numberKeyBindings`/modifier
  prefs (undo-stack.js `getUndoableSnapshot`); after load+undo, palette and
  counts return but bindings stay the cloud set. The confirm copy is written to
  only promise counters/lines/counts. Widening the snapshot would also change
  Clear-artboard behavior — out of scope, same stance as the dossier's Clear-copy
  amendment.
- **No-pages load** — pushUndoSnapshot no-ops; plan/apply walk zero pages;
  behavior degrades exactly to today's palette replace. Spec keeps this path.
- **fetch-before-confirm** — a user who cancels now still cost one read RPC;
  acceptable (read-only, and the warning numbers require the data).
- **Tier-1 interactions**: #1/#2 (backup/restore) touch the same
  counters/annotations state via `applyTakeoffBackupToState` — no shared code
  edited here, but land order doesn't matter since this branch only adds to the
  model factory. Item B13 (rename "Analyze My Usage"/"Palette Insights" →
  "My Standards") and dossier polish #8 (confirm/alert channel roulette) touch
  the same modal — keep copy edits here minimal so those PRs don't conflict.
  Esc-chain item (B1, paletteInsightsModal) is unrelated code.
- **Event allow-list drift** — if the migration ships but the client doesn't (or
  vice versa) nothing breaks: the RPC either drops the event or accepts a name
  nobody sends. Still ship both in one PR.
- **`state.rooms` / room boxes** — the artboard payload does not carry rooms;
  relink doesn't touch `roomId`; reconcile's existing room backfill still guards.

## Acceptance criteria

1. With a project open, 14 marks placed under counters/line types whose names
   exist in the cloud artboard under different ids: Load from Cloud → every
   tally in sidebar/Summary/legend shows the same non-zero numbers as before the
   load, now under the loaded items; zero marks render the orphan fallback.
2. A placed mark whose palette item has NO name match in the cloud artboard
   keeps counting under a visible "Unknown" row (yellow-circle counter / blue
   line) — no tally silently reads 0 anywhere.
3. The confirm dialog, when marks are placed, states the placed-mark count, the
   re-link-by-name behavior, the Unknown fallback (when applicable), and an undo
   promise limited to counters/lines/counts.
4. Immediately after Load, the undo button is enabled and Ctrl+Z restores the
   pre-load palette, marker keys, and counts.
5. With zero placed marks, behavior and confirm copy are unchanged from today
   (palette replace, bindings replace, no reconcile side-effects visible).
6. A successful load records one `artboard_load` row in `user_activity` with
   `relinkedMarks`/`orphanedMarks`/`counters`/`lineTypes` metadata (verify via
   the admin activity feed or `select` on the table after the migration).
7. Loading mid-bid marks the project dirty and the next autosave persists both
   the loaded palette and the relinked annotations.
8. `npm run check` passes; `npx playwright test my-settings.spec.js` passes,
   including both pre-existing tests unmodified in intent.
9. The artboard guide's Load-from-Cloud bullet documents the re-link and the
   Unknown fallback; FEATURES.md and FEATURE-CATALOG.md carry the one-line
   user-visible update.
