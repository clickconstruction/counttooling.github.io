# T1-12 — Dead view link: honest full-screen message

Plan of record for Tier-1 item #12 in JOURNEY-MAP.md ("Ranked improvement shortlist",
row 12, currently JOURNEY-MAP.md:200). Source dossier: journeys/share-with-an-outsider.md,
finding 1 (dossier line 59; rework proposal line 71; adversarial re-drive line 183).
Effort: S. Telemetry column: new `view_link_dead` event.

## Problem (verified)

A recipient who opens a dead, revoked, mistyped, or unreachable view link
(`/app/?t=TOKEN`) is walked through the full email gate, and only THEN told — via a
transient 5-second toast ("Failed to load: View link not found", or "Failed to load:
Failed to fetch" on network failure) — that nothing loaded. After the toast fades the
recipient sits in the **full empty estimating editor**: Upload PDF button, complete tool
row, gear, Sign In, zero error text anywhere in the DOM
(journeys/img/share-with-an-outsider-06.png). The sole failure handling is the catch in
[app.js:6389-6392](../../app.js) (`showToast('Failed to load: ' + (e.message || 'Unknown
error'), 5000)`), which wraps the whole `await App.initViewOnlyMode(viewToken)` boot
branch. The GC either concludes the app is broken or starts uploading their own PDF into
a tool they were never meant to drive — the sales funnel's worst outcome (J14).

Repro (from the dossier, reproduced twice independently, 2026-08-02 and 2026-08-09):
serve the repo statically, visit `/app/?t=deadtoken` with `get-view-project` stubbed
404 `{message:"View link not found"}` → gate → email → Continue → toast → after the fade,
the bare editor with no error surface. A second, subtler half: a **revoked** link whose
recipient has a cached snapshot never even fails — [features/view-only.js:237-239](../../features/view-only.js)
falls back to the IndexedDB view cache on ANY non-domain error, so "Revoke … It will stop
working immediately" (the Share dialog's own promise, share-links.js:146) is false for
returning viewers.

## Design

Replace the toast-over-empty-editor with a full-screen, plain-language failure surface,
distinguishing "the server said this link is dead" from "couldn't reach the server".
The failure UI lives in the feature file that owns the view-link session
(features/view-only.js); app.js keeps the single catch funnel and delegates to it
defensively per the registry conventions (AGENTS.md "Core-function → feature callbacks").

### 1. features/view-only.js — classify failures, own the screen

- **Tag server-rejected ("dead") errors** in `fetchViewProject`
  ([features/view-only.js:195-213](../../features/view-only.js)). Today the non-ok path
  throws three ways: `domain_restricted` (tagged `domainRestricted`, handled by the
  re-prompt loop — LEAVE UNCHANGED), `email_required` (:207-209), and the generic
  `throw new Error(data.message || 'Failed to load')` (:210). Change the last two so the
  thrown error carries `err.viewLinkDead = true` **only when `res.status` is 4xx**
  (404 not-found/revoked, 403, 410, and the email_required case). A 5xx stays untagged
  (transient server trouble → retryable). A network failure (`fetch` rejects with
  TypeError "Failed to fetch") is naturally untagged. `'Failed to load PDF'` (:258) and
  `'No PDF available'` (:265) stay untagged → retryable.
- **Honor revocation over the cache**: in the while-loop catch (:231-243), change the
  cache fallback branch from `else if (cachedProjectData)` to
  `else if (cachedProjectData && !(e && e.viewLinkDead))`. The comment at :221-224
  already states the intent ("Fall back to the cached snapshot only when the server is
  unreachable"); this makes the code match it. A dead-tagged error now propagates even
  when a cached snapshot exists.
- **New function `showViewLinkFailure(err)`** (registered as
  `App.showViewLinkFailure = showViewLinkFailure;` next to the other registrations at
  :306-310):
  - `const dead = !!(err && err.viewLinkDead);`
  - Set `#viewLinkDeadMessage` text:
    - dead: `This plan link isn't active anymore. Ask the person who sent it for a new one.`
      (exact copy from the shortlist row / dossier proposal line 71 — "plan link",
      "ask the person who sent it", no "fetch", no "error").
    - network/retryable: `Couldn't load this plan. Check your connection and try again.`
  - Show/hide `#viewLinkDeadRetry` (visible only when NOT dead); its click handler is
    `window.location.reload()` — the whole boot IS the retry loop, no bespoke re-fetch
    state machine.
  - Add class `visible` to `#viewLinkDeadScreen`.
  - Telemetry: `App.logUserEvent && App.logUserEvent('view_link_dead', null,
    { reason: dead ? 'inactive' : 'network' });` (see Telemetry section for gating
    reality and the required migration). `projectId` is `null` — the load failed, so no
    id exists client-side.

### 2. app.js — the catch delegates (app.js:6389-6392)

```js
} catch (e) {
  console.warn('[View link]', e);
  if (App.showViewLinkFailure) App.showViewLinkFailure(e);
  else showToast('Failed to load: ' + (e.message || 'Unknown error'), 5000);
}
```

- `console.error` → `console.warn`: this is a handled failure with a real UI now, and
  the Playwright specs assert zero console errors (view-only.spec.js `realErrors`
  would otherwise flag the new tests' expected path).
- The old toast survives only as the can't-happen fallback (feature file failed to
  load), matching the registry's defensive-callback convention.
- The `updateUI()` at :6393 and the `return` stay; the screen is independent of
  `updateUI` (it touches only its own elements).

### 3. app/index.html — the screen markup

Insert after the `viewLinkEmailModal` closing `</div>` (currently app/index.html:2378),
before `addCanvasModal`:

```html
<div id="viewLinkDeadScreen" class="view-link-dead-screen">
  <p id="viewLinkDeadMessage"></p>
  <button type="button" id="viewLinkDeadRetry" class="btn-yellow">Retry</button>
</div>
```

Deliberately NOT a `.modal-overlay`: no `showModal`/`hideModal`, no Escape wiring, not
dismissable, nothing behind it worth revealing. `btn-yellow` matches the gate's
Continue button (app/index.html:2375).

### 4. styles.css — the screen style

Next to the modal styles (near `.modal-overlay`, styles.css:475):

```css
.view-link-dead-screen { display: none; position: fixed; inset: 0; z-index: 400;
  background: var(--bg); align-items: center; justify-content: center;
  flex-direction: column; gap: 16px; padding: 24px; text-align: center; }
.view-link-dead-screen.visible { display: flex; }
.view-link-dead-screen p { color: var(--text); font-size: 1.05rem; max-width: 34em;
  margin: 0; }
```

`z-index: 400` sits above `.modal-overlay`/toasts (200, styles.css:475) and every menu
(300 — context/canvas/export menus, zoom rail) so nothing can paint over the message.
Opaque `var(--bg)` background: the empty editor underneath is fully hidden — the
misleading surface leaves this path entirely.

### 5. supabase/migrations — allow the new event type

`log_user_event` has a server-side event-type allowlist
([supabase/migrations/20260326230000_user_presence_and_activity.sql:53-56](../../supabase/migrations/20260326230000_user_presence_and_activity.sql))
— an unknown type raises `invalid event type` and the fire-and-forget `rpcSupabase`
call silently drops it. Add a new migration
`supabase/migrations/<timestamp>_log_user_event_view_link_dead.sql` that
`create or replace`s `public.log_user_event` identically but with `'view_link_dead'`
added to the `not in (...)` list (base it on the LATEST deployed function body —
earlier Phase-4 branches add their own event types via the same re-create pattern
(restore/scale/artboard events); copying the original 20260326230000 body would
silently break theirs. Keep the `security definer`, `set search_path`,
and the existing `grant execute … to authenticated`). Apply via the Supabase MCP
`apply_migration` tool (name = filename without `.sql`) per AGENTS.md.

### What does NOT change

- The email gate flow, including the `domain_restricted` inline-error re-prompt loop
  (view-only.js:232-236) — a rejected domain is a live link, not a dead one.
- Cancel/Escape at the gate (silent `return`, no throw) — the dead screen must NOT
  appear on cancel. That strand-in-the-editor is dossier finding 4, a separate
  proposal, not part of this item.
- The offline cache fallback for unreachable-server revisits (view-only.spec.js
  "offline fallback" test) — still serves the cached snapshot, no screen.
- The toast system (Tier-2 item 15's territory) — this change stops USING a toast on
  this path; it doesn't touch toast mechanics.
- Non-view-link boot, viewer-scale layer, hide-marks, everything else in the file.

### Simplicity budget

The failure path currently "offers" the recipient every editor affordance — Upload PDF,
the full tool row, Sign In — all of them wrong. The screen removes every decision except
the one honest next step (ask the sender / retry). No new modal machinery, no state, no
dismissal logic; Retry is a page reload, so the existing boot is reused as the retry
loop. The 5s failure toast leaves the path entirely.

## Tests

Extend **view-only.spec.js** (Playwright; it owns this surface and already stubs the
Edge Function via `routeViewProject`, view-only.spec.js:66-80). Per house naming,
`*.spec.js` = Playwright; no new spec file.

1. **`dead link: full-screen inactive message, no Retry, editor never exposed`** —
   `routeViewProject` returns `{ status: 404, body: { message: 'View link not found' } }`;
   goto `/app/?t=' + TOKEN`; `submitEmail(...)`; then assert:
   - `#viewLinkDeadScreen.visible` appears; `#viewLinkDeadMessage` text equals
     `This plan link isn't active anymore. Ask the person who sent it for a new one.`
   - `#viewLinkDeadRetry` is hidden.
   - `document.body` has no `has-pdf`; `App.state.isViewer === false`;
     `App.state.pages.length === 0`.
   - `localStorage['view:allowed:' + TOKEN]` is null (only persisted on success,
     view-only.js:229).
   - `realErrors(errors)` is empty (needs the `console.warn` change in app.js).
2. **`network failure with no cache: Retry shown, reload recovers`** — route
   `**/functions/v1/get-view-project` with `route.abort('failed')` (OPTIONS included);
   goto + `submitEmail`; assert screen visible WITH `#viewLinkDeadRetry` visible and the
   connection copy. Then `page.unroute` + `routeViewProject(page, () => ({ status: 200,
   body: projectPayload() }))`, click Retry, and — since the email was never persisted —
   `submitEmail` again and `expectViewerLoaded(page)`. Pins the full recover loop.
3. **Extend the existing `offline fallback` test** (view-only.spec.js:214-245): add one
   assertion that `#viewLinkDeadScreen` is not visible — cache-served revisits must
   never show the screen.
4. **Extend the existing `registry wired` test** (:106-118): add
   `failure: typeof window.App?.showViewLinkFailure` expecting `'function'`.
5. **(New) `revoked link with a cached snapshot shows the dead screen`** — first visit
   200 (populates the cache, as in the offline test), then re-route to 404
   `{message:'View link not found'}` and reload: assert the dead screen (not the cached
   viewer). This pins the honor-revocation-over-cache change.

Node unit tests: **none** — no pure logic is extracted (the classification is a
status-code tag at the throw site); everything observable is DOM/route behavior, which
the spec owns.

## Telemetry

- **New event: `view_link_dead`**, per the shortlist row. Emitted in
  `showViewLinkFailure` via the already-published `App.logUserEvent` (app.js:6158;
  implementation app.js:2742) with metadata `{ reason: 'inactive' | 'network' }`,
  `projectId` null.
- **Requires the allowlist migration** (Design §5) or the RPC rejects it server-side
  and the event silently vanishes. (Precedent: `render_worker_fallback` at app.js:1522
  is currently dropped this way — see Risks.)
- **Honest limitation, stated up front**: `logUserEvent` no-ops without a signed-in
  session (app.js:2743), and `log_user_event` is granted to `authenticated` only
  (migrations 20260326230000 + 20260724220000) — so the anonymous GC, the MAIN victim,
  emits nothing. The event still captures signed-in users hitting dead links (the
  `view_link_session_attached` population, app.js:6383). Full coverage of the
  107-links/56-accesses under-conversion question would need the `get-view-project`
  Edge Function to log dead-token attempts server-side (e.g. into
  `view_link_access_log` with a status column) — explicitly OUT of this item's scope;
  flag as a follow-up in the PR description.

## Risks & edge cases

- **Revocation-over-cache is a behavior change**: a revoked link's returning viewer
  loses the cached snapshot. This is the Share dialog's own promise ("It will stop
  working immediately") and the code comment's stated intent, but call it out in the PR.
  Transient 5xx responses must stay untagged (cache still serves) — hence the 4xx-only
  tag rule; get it wrong and a flaky server locks paying viewers out of cached plans.
- **`domain_restricted` must never reach the screen** — it is handled inside the
  re-prompt loop before the generic catch; the tag change must not touch that branch
  (spec test 'domain_restricted' guards it).
- **Gate cancel/Escape** returns without throwing → no screen (dossier finding 4 is a
  separate proposal; if it later re-shows the gate, no overlap with this surface).
- **SW mixed-shell reload** (app.js:6357-6360) can fire while the screen is up
  (`pages.length === 0`, not dirty) → page reloads → boot re-runs → screen re-appears
  or genuinely recovers. Harmless, arguably a free retry.
- **Signed-in user on a dead link**: the auth-attach block (app.js:6377-6388) is inside
  the same try and is skipped on throw — `view_link_dead` then fires only if
  `initSupabaseAuth` ran earlier in the session… in practice it has NOT on the `?t=`
  branch, so `state.supabaseSession` may be unset and even signed-in users may not emit.
  Accepted for S effort; the metadata/reason split still works whenever a session
  exists. Do not move auth init to fix telemetry — boot-order changes are out of scope.
- **Tier-1/2 interactions**: item 15 (toast rework) — no conflict, this path stops using
  toasts; item 1/2 (signed-out restore prompt) — different boot branch (`?t=` returns at
  app.js:6394 before the restore path). No shared lines with any in-flight ◐ item.
- **Known dropped event precedent** (out of scope, worth a follow-up note): app.js:1522
  logs `render_worker_fallback`, which the RPC allowlist rejects — it has never landed
  in `user_activity`. The new migration could add it in the same edit ONLY if the
  reviewer wants it; default is not to (one-topic discipline).

## Acceptance criteria

1. Visiting `/app/?t=<bad token>` (stub 404) and completing the email gate shows a
   full-screen opaque message reading exactly "This plan link isn't active anymore. Ask
   the person who sent it for a new one." — no Retry button, no toast needed, and none
   of the editor chrome (Upload PDF, tools, Sign In) is visible or clickable.
2. Same visit with the Edge Function unreachable (abort) and no cache shows the
   connection message WITH a Retry button; clicking Retry reloads and, once the server
   answers, the viewer loads normally after the gate.
3. A revoked link (server 404) with a previously-cached snapshot shows the dead screen,
   not the cached plan; an unreachable server with a cache still shows the cached plan
   with no screen.
4. The `domain_restricted` rejection still re-prompts inline at the gate (unchanged
   spec test passes).
5. Cancel/Escape at the gate still silently closes the modal with no dead screen.
6. `App.showViewLinkFailure` is registered; app.js's catch calls it defensively with
   the toast as fallback; the console line is `warn`, not `error`.
7. `view_link_dead` is in the `log_user_event` allowlist (migration applied) and the
   client emits it with `reason: 'inactive' | 'network'` when a session exists.
8. All view-only.spec.js tests (4 existing + 3 new/extended) pass; `npm run check`
   passes; `CACHE_VERSION` restamped via `npm run build:sw`.
9. ARCHITECTURE.md (Files row + View links bullet), FEATURE-CATALOG.md, and the
   sharing-and-view-links guide (rebuilt) all describe the new behavior; JOURNEY-MAP.md
   row 12 status updated.
