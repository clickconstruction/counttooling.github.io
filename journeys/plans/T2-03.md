# T2-03 — Hidden marks stop catching the mouse

Plan of record for Tier-2 item #25 (JOURNEY-MAP.md "Tier 2" row 25; Stage-2
re-rank slot **3** — "silent data mutation", S). Source dossier:
`journeys/annotate-and-review.md` (J8, Friction #3 — stumble, CONFIRMED twice:
walker drag moved a hidden note (229,148)→(261,180) with nothing painted;
adversarial re-drive moved a hidden note 32 pt and the move persisted after
re-show). Dossier proposal verified spiritPass:true — "an early
`if (state.hideMarks) return null` in hitTest covers notes, legend, and context
menus alike". Self-contained; read `AGENTS.md` first. Line numbers verified
2026-08-29 on this worktree; grep before editing (app.js is ~6.5k lines and
Tier-1 shipped since the shortlist was cut).

## Problem (verified)

The hide-marks eye blanks the *paint* but not the *pointer*. `toggleHideMarks`
(app.js:1553) flips `state.hideMarks`; `renderAnnotationsInner` sizes + clears
the overlay then early-returns (app.js:1631), so the sheet looks bare — but
`hitTest` (app.js:1058) never consults the flag, so every invisible mark still
answers the mouse at all five call sites: the NOTE-tool click that opens edit
(app.js:5128), the dblclick note edit (:5160), `handleContextMenu` → per-mark
menu (:5195), the Move-mode mousedown that starts legend/note/marker/line/zone
drags (:5461), and the mousemove hover-cursor swap (:5603). Net effect: a
reviewer skimming the "clean" drawing drags an unseen note or legend, gets
move/resize cursors over blank paper, and can right-click empty space into a
Delete menu for a mark they cannot see. The mutation is silent and persists
after re-show — exactly the "who moved my note" class the dossier confirmed.

## Design

One guard, first line of `hitTest` (app.js:1058), before the page lookup:

```js
function hitTest(pos, radius = 12) {
    // T2-03: hide-marks means the sheet is read-only-bare — invisible marks
    // must not catch the mouse. Mirrors renderAnnotations' early return.
    if (state.hideMarks) return null;
```

Because all five interaction paths funnel through this one function (hitTest is
app.js-internal — not on `App.*` or `window.*`, verified by grep), the single
guard fixes drags, resizes, note edits (click and dblclick), context menus, and
hover cursors at once. Callers already handle `null` (it is the everyday
"clicked bare paper" result), so no call site changes: Move-mode drags fall
through to the normal sheet pan, right-clicks open nothing, the cursor stays
default/crosshair.

**What does NOT change:** `toggleHideMarks` / `updateHideMarksButton` and the
view-token persistence (`view:hideMarks:<token>`); `renderAnnotationsToContext`
(exports/reports never hid marks and still don't); placement tools while hidden
(arming Counter/Line/etc. with hide-marks on still places marks invisibly —
existing behavior, deliberately untouched); the Ghost-tool drag path (it uses
`annotationModel.ghostIndexAtPoint` at app.js:5449, gated on `TOOL.GHOST` — a
deliberately armed editing tool, out of this item's scope); Delete Area's own
rect collection; features/drop-peek.js, which already self-gates on
`!state.hideMarks` (drop-peek.js:215) — the model this fix generalizes.

**Simplicity budget:** two lines of comment + one guard line; zero new UI,
state, settings, or copy. It *removes* an entire failure class (silent edits of
invisible marks) and the defensive habit of re-showing marks to check nothing
moved before trusting a reviewed sheet. Spirit test: fewer decisions (hidden =
inert, no exceptions to remember), trade framing ("the bare drawing is just a
drawing"), invisible fix, nothing to teach.

## Risks & edge cases

- **NOTE tool + hide-marks**: clicking atop a hidden note previously opened its
  editor (:5128); now it creates a *new* note at that spot (which won't paint
  until re-show). Consistent with bare-sheet semantics and with every other
  placement tool while hidden; accepted, noted here so the PR names it.
- **Viewers**: view-link sessions persist hide-marks per token; the guard makes
  a viewer's hidden legend un-draggable too — desired (viewers reading the bare
  drawing were the original victims). drop-peek is already gated, unchanged.
- **T2 #14 (drag-gesture rectangles, M)** edits the same mousedown/mouseup
  handlers but only tool-armed branches — no overlap with the hitTest guard;
  either order rebases cleanly. **T2 #27** (dblclick sheet rename) is sidebar
  DOM, not canvas — no overlap.
- **The future empty-legend polish** (dossier: don't draw a zero-row legend)
  must mirror its gate inside hitTest's legend block or the invisible "No
  items" box keeps catching the mouse (dossier verify note :209). This guard
  doesn't cover that case (hideMarks off, legend undrawn) — explicitly NOT in
  this PR; the plan for that batch item owns it.
- **Shipped Tier-1 behavior**: T1 ghost tool and drop-peek both self-gate
  around hide-marks already (see Design) — the guard duplicates neither and
  cannot double-fire; `state.hoverLegendResize` (:5604) goes false while
  hidden, which is correct for the resize-affordance paint that isn't painting
  anyway.

## Acceptance criteria

1. With marks hidden: dragging at a hidden note/legend/marker position moves
   nothing — the gesture pans the sheet; after re-show, every mark is exactly
   where it was (the dossier's 32-pt silent move is unreproducible).
2. With marks hidden: right-click anywhere on the sheet opens no per-mark
   context menu; dblclick opens no note editor; the cursor never shows
   move/resize/ns-resize over hidden marks.
3. With marks shown: drags, resizes, note edit (click and dblclick), context
   menus, and hover cursors behave exactly as today (control assertions in the
   extended spec pass).
4. Exports, reports, and the report/export bundling of highlights/notes are
   byte-identical with hide-marks on or off (renderAnnotationsToContext path
   untouched).
5. `npm run check` passes (incl. build:guides and build:sw stamps); the full
   Playwright suite passes locally; `hide-marks.spec.js` carries the new
   inertness test.
