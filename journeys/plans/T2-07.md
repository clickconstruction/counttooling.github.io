# T2-07 — Quick Count stops minting identical marks

Plan of record for Tier-2 item **#16** (JOURNEY-MAP.md "Tier 2" row 16; Stage-2
re-rank slot 7). Source dossier: `journeys/count-fixtures.md` (J4, Friction #2,
CONFIRMED — "0.5in PEX Tee" came out with icon AND color strictly equal to Water
Closet's; the error surfaces at pricing time, not counting time).

Self-contained: read `AGENTS.md` first for house conventions. Anchors below
re-verified 2026-08-29 on the app-review worktree; re-grep before editing.

## Problem (verified)

`features/quick-modals.js` — the Quick Count Add handler (`:223-244`) mints
`{ id, name, icon, color }` where `icon` comes from the selected grid cell and
`color` is `mods.defaultColor || App.COLORS[2]` (`:234`, `#e8c547` yellow). The
grid pre-selects the **first** library icon (`:114` — `(ic, i) => i === 0`, the
toilet), so unless the user deliberately picks a cell or has bound an icon to the
Type via the "?" box (`iconByType`, applied at `:139`), every Quick Count counter
gets first-icon + default-yellow — indistinguishable on the sheet from a stock
"Water Closet" counter. The dossier's caveat is binding: the Type list is
user-editable (`:200-210` adds arbitrary types), so any fix keyed to stock type
names cannot carry custom types. Note: a per-Type default **icon** map
(valve/elbow glyphs) is not shippable small — `icons.js` has no valve or elbow
art (grep of `terms`: only `'tee'` → Three Way Diamond and `'pipe'` → Pipe), and
authoring new bundled glyphs blows the S budget. The color-rotate fallback is the
half the verify pass called the part that must carry custom types; it is the fix.

## Design

One rule: **Quick Count never creates a counter whose icon+color exactly matches
an existing counter — the color rotates to a free palette entry, and the panel
previews the color that will actually mint.**

### `recent-colors.js` (pure color-behavior module) — one new helper

Beside `nextRecentColors`, exported in the existing guarded CommonJS footer:

```js
// First palette color used by NO existing counter (case-insensitive compare
// against counter.color). When every palette entry is in use: the entry after
// `current` (wrapping; palette[0] when current is off-palette). Pure — shared
// by Quick Count (T2-07) and the Create-tab twin guard (T2-05 #17).
function nextUnusedCounterColor(counters, palette, current) { … }
```

No eslint or registry work: the features lint group already spreads
`recent-colors.js` exports as readonly globals (eslint.config.js:47, :200-208),
so feature files call it bare — same as `features/line-color.js` does with
`nextRecentColors`. No `App.*` publish, no app.js edit.

### `features/quick-modals.js` — resolve the effective color once, use it twice

- New private `getCounterQuickCountEffectiveColor(iconPath)`: base =
  `mods.defaultColor || App.COLORS[2]`; if any `App.state.counters` entry has
  `icon === iconPath` and the same color (lowercased compare), return
  `nextUnusedCounterColor(App.state.counters, App.COLORS, base)`; else base.
- **Add handler** (`:230-234`): keep the existing `icon` computation verbatim;
  `color: getCounterQuickCountEffectiveColor(icon)` replaces the inline default.
- **Preview WYSIWYG** (`updateCounterQuickCountNamePreview`, `:48-63`): the icon
  preview fill (`:58-59`) and the swatch background (`:62`) use the effective
  color for `getCounterQuickCountEffectiveIconPath()`; when it differs from the
  base, set the swatch `title` to
  `"Color adjusted so these marks don't match an existing counter"`.

**What does NOT change:** the swatch click still edits `mods.defaultColor`
seeded with the base color (`:142-151`) — rotation is per-create and is **never
written back** to `plumbingModifiers` (which ride the Artboard, app.js:3054);
explicit icon selection and the `iconByType` "?"-box binding are respected as
today (a deliberately distinct icon means no rotation fires); the pre-existing
deleted-bound-icon edge (preview shows the `iconByType` path while Add falls to
icon[0], `:44-46` vs `:231`) stays as-is; `counter_marker_added`; undo
(`pushUndoSnapshot` already precedes the create); Quick Keys (id-keyed).

**Simplicity budget (spirit test):** ~12-line pure helper + ~10 lines in
quick-modals; zero new UI, zero dialogs, zero settings, zero events. It removes
the identical-marks failure class, the pricing-time forensic "which yellow toilet
is the Tee?" audit, and the mandatory "?"-box detour on the common path (test 1:
fewer decisions; test 4: automatic, nothing to find). Trade framing: two
different fittings never look like one on the sheet.

## Risks & edge cases

- **T2-05 (#17, re-rank slot 5 — lands first)** ships a *private* twin-guard
  rotate in `features/counter.js` with the same stated semantics and an explicit
  note that #16 will lift it. On execution: move/replace that private function
  with the shared `nextUnusedCounterColor` (counter.js is a features file — bare
  global works there too). If T2-05 has NOT landed yet, this plan is still
  self-contained; T2-05 then consumes the helper instead of minting its own.
- **All 18 palette colors used with the same icon**: the wrap fallback can still
  collide — degenerate, accepted (same stance as T2-05).
- **Deliberate twins**: a user who *wants* two identical-looking counters can
  recolor either one afterward via counter settings/details — no dialog, no
  blocked workflow (matches T2-05's no-dialog convention).
- **Custom off-palette `defaultColor`** (set via the swatch's color modal): the
  dupe compare is against the base color itself, rotation searches `App.COLORS`
  only — deterministic, and the user's saved default is untouched.
- **Programmatic counter creation in specs** (sidebar-lists, ghost,
  palette-insights push into `state.counters`): unaffected — rotation lives only
  in the Quick Count Add click handler.
- **Shipped Tier-1 interactions**: T1-09's artboard-load reconcile matches by
  name, not color — unaffected. No overlap with any other queued T2 unit's
  files except T2-05's counter.js (above).

## Acceptance criteria

1. Fresh project with "Water Closet" (icon[0], `#e8c547`): Quick tab → Add
   Counter with nothing touched → the new "0.5in PEX Tee" keeps the type icon
   behavior it has today but its color is NOT `#e8c547`; its marks and sidebar
   row are visually distinct from Water Closet's.
2. Repeating Add for other Size/Type/Material combos never yields two counters
   with identical icon+color.
3. Deliberately selecting a distinct icon (or a Type with a bound "?"-box icon)
   → color stays the saved default; no rotation.
4. A user-added custom type gets the same protection (no stock-name dependence).
5. The panel's icon preview and swatch show the exact color that will mint,
   before Add is clicked.
6. `plumbingModifiers.defaultColor` in localStorage (and the Artboard) is never
   changed by a rotation.
7. `npm run check` passes; `quick-modals.spec.js`, `counter.spec.js`, and
   `create-color-picker.spec.js` pass locally.
