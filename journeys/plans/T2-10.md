## Problem (verified)

All five rectangle tools — Highlight (H), Multiply Zone (X), Scale Zone, Room
Sizer (V), Delete Area — are two-click-only state machines inside
`handleCanvasClick` (app.js:4923; branches at :4995 highlight, :5012 multiply,
:5043 scale zone, :5075 room, :5093 delete). A press-drag-release — the first
gesture every untrained hand tries, and the gesture two guides literally promise
("drag a rectangle", content/guides/fixing-mistakes.md:30 and
scale-zones-and-multiply-zones.md:18/27 — currently false advertising) — does
this instead: mousedown does nothing for these tools (no branch claims it),
mouseup does nothing, and the browser's trailing **click** event fires at the
release point, arming corner 1 *there* (the drawn rectangle is wholly discarded).
The user sees nothing appear, concludes the tool is broken, and their recovery
click completes a large unintended rectangle from wherever they let go — a stray
422×391-pt highlight (J8, screenshot-verified), an unintended zone previewing
"In this area: 0 counter(s)" (J6), or a Room Size dialog reading
0'-0" × 0'-0" · 0.0 ft² (J7 — reproduced under fast, slow-into-loupe, and
human-paced drag timings; `openRoomBoxModal` (features/room-sizer.js:176) has no
minimum-size guard). The only coaching is 11px status-bar text ("Click first
corner / Click second corner"). Live rubber-band previews already exist for all
five tools (app.js:1857-1913, including the Room Sizer's L×W readout) — but only
after corner 1 is set, so the failed drag never shows one. Four journeys hit
this on their happy paths; per the 2026-08-30 re-rank it is the widest-spread
M item left in the tier.

Constraint verified in code: mousedown on these tools already starts the 280ms
aim-loupe timer (app.js:5506-5512, `AIM_PRESS_MS` :5216 — all five rectangle
tools are `isAimingTool()` members, :5224-5245), and moving >6 client px before
it fires cancels the loupe (:5528-5530). So "drag" and "press-hold-aim" already
share the mouse-down and are disambiguated by that 6px/280ms race — the drag
gesture must slot into the loser's bracket, not fight the loupe.

## Design

One shared gesture, implemented once in the mouse handlers (app.js
"SECTION: Canvas mouse, wheel & touch handlers", :5432): **press-drag past a
threshold arms corner 1 at the press point and completes the rectangle at the
release point.** A quick click (no movement past threshold) behaves byte-for-byte
as today, so the two-click path — and every existing Playwright spec that places
rects with two `mouse.click`s — is untouched. Touch is untouched entirely
(separate `touchstart`/`handleTouchAsCanvasTap` path, :5792/:5903 — tap-tap
stays the mobile gesture). Plus one guard: the Room Size dialog refuses
~zero-size boxes.

### Part 1 — drag completes the rectangle (app.js only)

Constants, beside `AIM_PRESS_MS` (:5216), same local style:

```js
const RECT_DRAG_MIN_PX = 6;   // client px; matches the aim-timer move-cancel threshold
                              // so "drag" and "hold-to-aim" can never both claim a gesture
const RECT_TOOL_START_KEY = { [TOOL.HIGHLIGHT]: 'highlightStart',
  [TOOL.MULTIPLY_ZONE]: 'multiplyZoneStart', [TOOL.SCALE_ZONE]: 'scaleZoneStart',
  [TOOL.ROOM]: 'roomBoxStart', [TOOL.DELETE_ZONE]: 'deleteZoneStart' };
```

State (app.js:180 literal): add `rectPress: null` (`{ pdf, client }`),
`rectDragging: false`, `justFinishedRectDrag: false`.

**mousedown** (:5506, inside the existing `isAimingTool()` else-if, after the
aim timer is set — the hit-test branches above it keep priority, so note/legend
grabs still win): when `RECT_TOOL_START_KEY[state.tool]` exists AND that start
is currently null AND `isPointInPageBounds(pdf)`, record
`state.rectPress = { pdf: state.mousePos, client: c }`. (If a corner is already
pending, do nothing — a drag then completes at the release point via the
trailing click, exactly as today, which is correct behavior.)

**mousemove** (:5528, extend the existing aim-cancel block): when the >6px move
cancels `aimPressTimer`, promote a pending `rectPress`:

```js
if (state.rectPress && RECT_TOOL_START_KEY[state.tool]
    && !state[RECT_TOOL_START_KEY[state.tool]]) {
  state[RECT_TOOL_START_KEY[state.tool]] = state.rectPress.pdf;  // corner 1 = PRESS point
  state.rectDragging = true;
}
state.rectPress = null;
```

From here the existing preview branch (:5600) draws the live band + Room
readout on every move — zero new draw code. The Scale-Zone/Room scale gates
can't be hit here (those tools can't be armed on an unscaled page — arm-time
gate plus T1-05's page-switch disarm), so no extra check.

**mouseup** (:5623, after the `state.aiming` early-return at :5631 and the
quick-click timer clear at :5641): complete the drag:

```js
if (state.rectDragging) {
  state.rectDragging = false;
  const key = RECT_TOOL_START_KEY[state.tool];
  if (key && state[key]) {   // Esc mid-drag cleared the corner -> gesture is dead
    const pt = canvasPointFromEvent(e);
    const pdfUp = clampPointToPageBounds(canvasToPdf(pt.x, pt.y));  // same clamp the loupe uses (:5264)
    handleCanvasClick(null, pdfUp);   // corner-2 path: dialogs, undo, overlap checks — all reused
    pushSaveEvent('rect_drag_complete', 'Rectangle completed by drag', JSON.stringify({ tool: state.tool }));
  }
  state.justFinishedRectDrag = true;   // swallow the trailing native click
  return;
}
state.rectPress = null;   // sub-threshold press: plain click, two-click path handles it
```

Routing completion through `handleCanvasClick(null, pdf)` is the load-bearing
choice: it is the exact pdfOverride path the aim loupe already commits through
(`commitAimPoint`, :5250-5253), so overlap toasts, undo snapshots, dirty
marking, the "In this area" previews, and every dialog open identically for
drag, click-click, and loupe. The clamp prevents the one divergence: a release
outside the page would otherwise hit the branch's `isPointInPageBounds` bail
and strand a phantom corner.

**click suppression** (:5727-5728): add `state.justFinishedRectDrag` to the
flag list, both the compound `if` and the reset lines (the
`justFinishedDragGhost` pattern, comment at :5655-5660 explains why).

**mouseleave** (:5683): if `rectDragging`, cancel the whole gesture — clear
`rectDragging`, `rectPress`, AND the armed start key (band vanishes; no phantom
corner survives the exit). Mirrors `cancelAiming` semantics.

**cancelAiming** (:5272): add `state.rectPress = null;` beside the existing
`aimMouseDownClient` clear — a hold that entered the loupe must not later
promote into a drag.

Loupe coexistence (the row's named constraint), stated as the rule the code now
enforces: **hold still 280ms → loupe wins** (precision path; release commits ONE
corner via `commitAimPoint`, drag machinery inert because promotion only runs
while `aimPressTimer` is pending); **move >6px before 280ms → drag wins** (loupe
timer dies in the same block that promotes the press). One constant, one block,
no race.

### Part 2 — refuse the ~zero-size Room dialog (features/room-sizer.js)

At the top of `openRoomBoxModal(rect)` (features/room-sizer.js:176):

```js
// A ~zero-size box is a mis-click (drag-release + tap-same-spot both produce
// them) — refuse the dialog instead of offering 0'-0" x 0'-0" (J7 friction #5).
const zoom = App.state.zoom || 1;
if (Math.abs(rect.x2 - rect.x1) * zoom < 6 && Math.abs(rect.y2 - rect.y1) * zoom < 6) return;
```

Both-dims-under-6-logical-px only — a thin sliver room (long in one dimension)
stays legal. Guarding inside the feature entry point covers all three callers at
once: the mouse chain (app.js:5084), the duplicated touch-tap chain (:5978), and
the new drag path. Callers already cleared `roomBoxStart` and leave the tool
armed, so the refusal reads as "nothing happened — click again": status returns
to "Click first corner", no toast, no new copy. (The drag path can't produce a
both-dims-degenerate rect anyway — the 6px threshold guarantees one dimension —
so this guard exists for the two-click/tap-tap trap.)

### What does NOT change

- The two-click path: a movement-free click sequence executes today's code
  byte-for-byte (the press is recorded and silently discarded at mouseup).
- Touch: `touchstart`/`touchmove`/`handleTouchAsCanvasTap` untouched — tap-tap
  stays the mobile gesture (JOURNEY-MAP: "two-click stays for touch").
- The aim loupe: `AIM_PRESS_MS`, `enterAiming`, `commitAimPoint` all untouched;
  the loupe still commits single corners (aim-loupe-desktop.spec.js "Highlight:
  two holds commit one rect" must pass unmodified).
- The five band previews (:1857-1913) including the shipped `#e85447` fix.
- Ghost tool (`ghostRectStart`) and Chain: two-corner but NOT rectangle-completion
  tools — Ghost's mousedown already implements its own drag semantics (:5449),
  so drag-complete there would collide. Deliberately out of scope.
- Multiply/Scale-Zone empty-rect no-op zones (J6 papercut #8): not in this row's
  proposal — the drag threshold makes them unreachable by drag, and the
  two-click empty-zone case stays as-is.
- Esc behavior, undo granularity, dialogs, all copy — zero new words anywhere.
- `handleTouchAsCanvasTap`'s duplicated tool chain: not consolidated here.

### Simplicity budget

No new UI, no new modal, no new copy, no new file (test aside): ~45 lines in
app.js (one map, three fields, four handler insertions) + 4 lines in
room-sizer.js. It retires an entire failure cascade — the "is it broken?"
pause, the phantom corner at the release point, the stray rectangle the
recovery click paints, and the 0'×0' dialog — and makes two guides' existing
"drag a rectangle" wording true instead of adding explanation. Spirit test:
(1) 3 actions → 1 gesture; (2) no new words; (3) removes the need to read
status-bar micro-text; (4) drag-a-box is what an unguided hand tries first.

## Tests

House naming (playwright.config.js `testMatch`): `*.spec.js` = Playwright,
`*.test.js` = Node. No pure helpers are added, so no Node tests; the gesture is
browser-event plumbing and belongs to Playwright.

**New `rect-drag.spec.js`** (no existing spec owns cross-tool canvas gestures —
precedent: T1-05's scale-gate-page-switch.spec.js). Using `page.mouse.down()` /
`move()` (multiple steps) / `up()`:
1. Highlight drag: press at A, drag 120px, release at B → exactly one highlight
   stored with corners ≈ A and B (pdf-space tolerance), `highlightStart` null,
   and a subsequent single click arms a fresh corner (no leftover suppression).
2. Two-click regression: two separated clicks → a second highlight; a
   sub-threshold "drag" (3px) arms corner 1 only, exactly like a click.
3. Delete Area drag around placed counters → `#deleteZoneModal` opens with the
   correct "In this area:" counts; Cancel leaves marks intact.
4. Multiply Zone drag → `#multiplyZoneModal` opens; the zone rect matches
   press/release points after Apply.
5. Room drag on a scaled page → `#roomBoxModal` opens with non-zero L×W.
6. Loupe coexistence: press and hold ≥350ms with no movement → `#aimLoupe`
   visible; then drag and release → NO completion, exactly one pending corner
   (`roomBoxStart`/`highlightStart` set), matching today's loupe contract.
7. Release outside the page bounds after a drag → rectangle completes clamped
   to the page edge; no phantom corner remains.

**Extend `room-sizer.spec.js`** (owns `openRoomBoxModal`): two clicks at the
same point (and at 3px apart) → `roomBoxModal` stays hidden, tool stays
`TOOL.ROOM`, `roomBoxStart` null; two clicks 200px apart still opens it.

**Must-pass untouched** (run locally, no edits expected):

## Risks & edge cases

- **Aim loupe (shipped Tier-1-adjacent behavior)**: the single highest-risk
  seam. The rule is mechanical (280ms/6px, one shared constant) but the
  aim-loupe specs are the contract — if any fails, the promotion block's
  placement relative to the timer-cancel is wrong. Do not change `AIM_PRESS_MS`
  or the 6px literal's aim semantics; reuse the literal via `RECT_DRAG_MIN_PX`
  only if it reads cleanly, otherwise leave the aim line alone.
- **Esc mid-drag**: the Esc ladder clears pending starts while the button is
  still down; mouseup's `state[key]` re-check (Design) makes the gesture die
  cleanly instead of arming a corner at the release point. Covered implicitly;
  add an assertion to rect-drag test 1's cleanup if cheap.
- **Existing specs that click-click rects**: `mouse.click()` is down+up at one
  point → sub-threshold → two-click path unchanged. Specs that `dispatchEvent`
  a bare click never set `rectPress` at all. No churn expected.
- **T2 #25 (hidden-marks hitTest early-return)** edits `hitTest` — our
  mousedown reads `hitTest` results *before* the aim branch but adds no branch
  of its own there; rebase is trivial, no logic overlap.
- **T2 #15 (toast rework)**: no interaction — this plan adds no toast (the Room
  refusal is deliberately silent).
- **B8 rider** ("zone tools stay armed after Apply with a visible armed hint —
  ship only with T2 #14"): this IS T2 #14's build. If B8's rider is wanted in
  the same PR, it is a separate small commit on the same branch; this plan does
  not implement it and nothing here blocks it.
- **Duplicated touch chain** (`handleTouchAsCanvasTap`, :5903): the Room guard
  covers it via the shared feature entry; the other tools' touch behavior is
  intentionally unchanged. Any future consolidation is out of scope (the
  decomposition audit owns that).
- **Viewer sessions**: viewers can't arm these tools and the mousedown
  aim-branch's viewer guard (:5506) blocks recording anyway — drag machinery is
  inert in view links.
- **Middle/right-button drags**: mousedown gates on `e.button === 0` (:5443)
  before the aim branch — pan and context-menu are unaffected.
- **`pushSaveEvent` availability**: the app.js wrapper exists at :525 and is
  callable from the mouse handlers (same IIFE); no registry publish needed.
- **Legit tiny rooms**: the refusal needs BOTH dims under 6 logical px at the
  current zoom — anyone drawing a real closet zooms in past that. If a spec or
  Will hits a false refusal, the threshold is one constant.

## Acceptance criteria

1. With Highlight armed: press-drag-release beyond ~6px leaves exactly one
   highlight whose corners are the press and release points; the live yellow
   band is visible during the drag; the next click starts a fresh rectangle
   (no phantom corner, no stray rect — the J8 cascade is gone).
2. The same gesture with Multiply Zone / Scale Zone / Delete Area / Room Sizer
   opens each tool's normal dialog with the dragged rect (overlap toasts, "In
   this area" previews, undo, and dirty-marking identical to two-click).
3. Two separated clicks still complete a rectangle on all five tools —
   unchanged behavior, existing specs green without edits.
4. Press-and-hold ≥280ms without moving still summons the aim loupe; releasing
   commits a single corner; a drag after the loupe appears never
   drag-completes. All aim-loupe-desktop.spec.js tests pass unmodified.
5. Room Sizer: two clicks (or taps) at ~the same spot open NO dialog — the tool
   stays armed and coaching returns to "Click first corner"; a 0'-0" × 0'-0"
   Room Size dialog is unreachable by any input path.
6. Releasing a drag outside the page completes the rectangle clamped to the
   page edge; leaving the canvas mid-drag cancels the gesture entirely.
7. Touch: tap-tap still draws rectangles on all five tools (no touch-path diff
   in the PR).
8. With Supabase enabled, each drag-completion appends a `rect_drag_complete`
   entry visible in the Save Status modal log and the exported logs envelope;
   the code carries the TEMP removal comment. No `user_activity` event, no
   migration file exists in the PR.
9. `npm run check` passes; full Playwright suite passes locally; `git diff`
   touches only app.js, features/room-sizer.js, the new spec, room-sizer.spec.js,
   the three guide sources + generated guides, ARCHITECTURE.md, and the
   generated sw.js stamps.
