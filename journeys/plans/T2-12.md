## Problem (verified)

Two halves of one dialog:

1. **The tax.** `#polylineBtn.onclick` (app.js:3289-3300; the P hotkey and
   `#polylineBtnSidebar`:3382 both route through it, and the data-driven hotkey
   table clicks the same button — app.js:6244-6249) *always* populates and
   opens `polylineModal`, even when the user has a line type active in the
   sidebar (`state.activeLineTypeId`, set by `setActiveLineType` app.js:2597
   and by the picker/Quick-Keys/Chain surfaces). "Start Drawing"
   (app.js:3757-3766) then seeds `state.drawingPolyline` and arms
   `TOOL.POLYLINE`. So every bending run costs a modal round-trip that Quick
   Line (L) never charges — L arms instantly off the active type. And because
   `finishPolyline` (app.js:3770-3784) drops to `TOOL.NONE`, the *next*
   polyline pays the dialog again: the daily bending-run rhythm is
   dialog → trace → Move → dialog → trace → Move.
2. **The "—" trap.** With `state.lineTypes` empty, the dialog's select is
   populated with the fallback `'<option value="">—</option>'` (app.js:3294)
   and Start Drawing proceeds anyway: `lineTypeId` resolves to `undefined` →
   stored as `null` (:3758, :3762). The committed run appears in no Line Types
   tally and lands under Lines → "Unassigned" — the footage seems to vanish.
   The sibling Quick Line picker already handles this state properly with
   `#chooseLineTypeEmpty` (app/index.html:1387: "Add a line type first using
   **Create** or **Quick**."), but the polyline dialog lets you through.

A third, adjacent footgun verified in code while planning: pressing P *mid-draw*
reopens the dialog, and Start Drawing **replaces** `state.drawingPolyline`
wholesale — silently discarding every clicked vertex (:3762). The same
work-loss class T2-02 killed for Esc.

## Design

Three parts, one file each plus specs. No new modal, no new state fields, no
registry additions.

### Part 1 — active line type ⇒ P starts drawing immediately

`app.js` — in `#polylineBtn.onclick` (:3289), after the existing Set-Scale gate
(unchanged, still first), branch before the dialog population:

```js
document.getElementById('polylineBtn').onclick = () => {
  if (!getPageScale(state.currentPage)) { showSetScaleFirstToast('Polyline'); return; }
  if (state.drawingPolyline) { state.tool = TOOL.POLYLINE; updateUI(); return; }  // Part 2
  const lt = state.lineTypes.find(l => l.id === state.activeLineTypeId);
  if (lt) {
    // T2-12: a line type is active — P behaves like L: no dialog, the run
    // takes the type's color and an auto-name; the dialog stays reachable
    // by pressing P with no active type. (JOURNEY-MAP Tier-2 #28)
    state.drawingPolyline = { id: uid(), name: nextPolylineName(), color: lt.color,
      points: [], closed: false, lineTypeId: lt.id, group: state.activeGroupId || null };
    state.tool = TOOL.POLYLINE;
    updateUI();
    return;
  }
  /* existing dialog population + showModal('polylineModal') — unchanged */
};
```

`nextPolylineName()` — small private helper beside `finishPolyline` in the
`// SECTION: Polyline modal & drawing` region (no section marker moves):

```js
// Auto-name for dialog-skipped polylines: "Polyline N", N = project-wide
// polyline count + 1. Cosmetic; collisions after deletes are fine.
function nextPolylineName() {
  let n = 0;
  for (const p of state.pages) for (const c of (p.canvases || [])) n += (c.annotations?.polylines?.length || 0);
  return 'Polyline ' + (n + 1);
}
```

The object literal is field-for-field the Start-Drawing shape (:3762) — same
`group` stamp, same `closed: false` — so finish/draw/save/export paths see
nothing new. The sidebar's active-type highlight (sidebar-lists.js:152) stays
lit while tracing, which is now *truthful*: the run belongs to that type.

**Dialog reachability** (the "cases that need it"): press P with **no** active
line type — the dialog opens exactly as today (custom name, different type,
different color). Deactivating a type is one sidebar click (`setActiveLineType`
toggle, app.js:2597). No new affordance needed.

### Part 2 — an in-flight draft is resumed, never replaced

The `if (state.drawingPolyline)` line in Part 1: any P press while a draft
exists just re-arms `TOOL.POLYLINE` and returns — covering (a) re-press
mid-draw (today: reopens the dialog, where Start silently nukes the vertices)
and (b) the orphan draft the shipped T1-05 page-switch disarm can leave
(app.js:1285-1300 sets tool NONE but leaves `drawingPolyline` set). Finishing
or unwinding the draft (Enter / T2-02's staged Esc / M) remains the way to
start fresh. This deletes the last route by which the dialog could destroy an
in-flight trace.

### Part 3 — block Start Drawing on "—" (zero line types)

- `app/index.html` — inside `#polylineModal`'s first `.form-group` (:734-738;
  after T2-08 has removed the dead `#polylineNewLineType` link from this same
  block), add a hidden empty-state line, copy **identical** to
  `#chooseLineTypeEmpty` (:1387):

  ```html
  <p id="polylineEmpty" style="display:none;color:var(--text2);font-size:0.9rem;margin-top:8px;">Add a line type first using <strong>Create</strong> or <strong>Quick</strong>.</p>
  ```

  (Create/Quick are the Line picker's tabs, one L press away — same words the
  user already sees there; inline `display:none` toggled by JS is the house
  pattern this modal's sibling uses.)
- `app.js` — in the dialog-population branch of `#polylineBtn.onclick`, after
  building the select (:3294): `const none = state.lineTypes.length === 0;`
  then `document.getElementById('polylineEmpty').style.display = none ? '' : 'none';`
  and `document.getElementById('polylineStart').disabled = none;`.
- `app.js` — belt-and-braces in the Start handler (:3757-3758): replace the
  silent null-commit with a hard guard —
  `const lineTypeId = document.getElementById('polylineLineType').value || state.lineTypes[0]?.id; if (!lineTypeId) return;`
  and drop the now-dead `|| null` in the literal (:3762 keeps `lineTypeId`).

**What does NOT change:** the Set-Scale gate and its ordering (:3290-3293, and
the T1-05 page-switch re-check :1285-1300); `finishPolyline` still drops to
Move — **deliberate**: the verified proposal cures the tax by making the next
run a single P press, and auto-rearming on Enter would put a live pen in the
hand of someone reaching for the mouse (not verified, not in scope);
the dialog's name/color rows and Cancel; the Esc ladder (T2-02's staged branch,
app.js:6339 region — keyed on `state.drawingPolyline`, tool-independent, so it
unwinds immediate-armed drafts identically); `moveReset` / tool-switch /
viewer wholesale clears (:6178, :2249); right-click on `#polylineBtn` (Line
Type settings, tool-context-menu.js:76); `HOTKEYS` — the P row's "Polyline
mode" label stays accurate, so **no build:macros**; `logLineAddedEvent`
(app.js:2948) untouched; viewer gating (P is not `viewerAllowed`; the button
is in `viewerHideIds`); save/load/export — no shape change.

**Simplicity budget (spirit test #3):** removes a modal from every repeat
bending run — the app's heaviest polyline path collapses from
P → dialog → Start → trace to P → trace, and P now behaves like L (one mental
model for both line tools); removes the "Unassigned footage" trap class
outright (a polyline can no longer be created type-less); removes the
Start-Drawing-nukes-my-vertices footgun. Adds one hidden `<p>` reusing existing
copy and one tiny helper; net UI surface goes down by one dialog appearance per
run.

## Tests

House naming (playwright.config.js `testMatch`): `*.spec.js` = Playwright,
`*.test.js` = Node. No pure module changes → no unit test.

**`polyline-arm.spec.js` (new — no existing spec owns the polyline arm/dialog
surface; T2-02's `polyline-esc.spec.js` owns Esc only).** Boot: upload
`test-2pages.pdf`, seed `p.scale` + `s.lineTypes = [{ id:'lt1', name:'Test',
color:'#4a9eff', curveStyle:'straight' }]` (the snap-angles.spec.js:24-39
pattern), console-error capture in every test (needs the `config.local.js`
stub — AGENTS.md):

1. **Immediate arm** — set `activeLineTypeId = 'lt1'`, click `#polylineBtn`:
   `#polylineModal` never gets `.visible`, `state.tool === TOOL.POLYLINE`,
   `drawingPolyline` is `{ name: 'Polyline 1', color: '#4a9eff', lineTypeId: 'lt1' }`;
   three canvas clicks + Enter commit one polyline whose `lineTypeId` is
   `'lt1'`; the Lines list groups it under "Test", not "Unassigned".
2. **Auto-name increments** — arm again after the commit: draft name is
   `'Polyline 2'`.
3. **Dialog still reachable** — `activeLineTypeId = null`, click
   `#polylineBtn`: `#polylineModal.visible`, `#polylineStart` enabled,
   `#polylineEmpty` hidden; Start arms with the select's type (today's flow).
4. **"—" blocked** — `s.lineTypes = []`, `activeLineTypeId = null`, click
   `#polylineBtn`: modal opens, select shows "—", `#polylineEmpty` visible
   with the picker copy, `#polylineStart` disabled; `page.evaluate` a forced
   `.click()` on it → `drawingPolyline` stays null (the handler guard). No
   polyline can be committed.
5. **Draft resumed, never replaced** — immediate-arm, click 2 vertices, press
   P again: the 2 vertices survive and the modal never opens; simulate the
   orphan (set `state.tool = 0` with the draft in place), press P: same draft,
   tool re-armed.

## Telemetry

**None** (per the shortlist row — no new events, no allowlist migration, no
Save-Status counters). Free accuracy win worth stating in the PR:
`logLineAddedEvent` (app.js:2948) stamps `lineTypeId: state.activeLineTypeId
|| null`, which today logs `null` for every dialog-armed polyline; on the
immediate path the active type is set, so `line_added` payloads for polylines
become truthful with zero code change.

## Risks & edge cases

- **T2-02 (#22, shipped)**: its Esc branch is keyed on `state.drawingPolyline`
  alone, so staged unwind works identically for immediate-armed drafts; its
  `polyline-esc.spec.js` arm path needs the one-line update above.
- **T2-08 (#20, shipped)**: removed `#polylineNewLineType` from the same
  index.html block Part 3 edits — rebase is textual only. If order ever flips
  and the dead link is still present, leave it to T2-08; this plan neither
  wires nor removes it.
- **T2-09 (#21, shipped)** edits the footer hint slot (status-bar.js:166,
  `'Click to add points'` for POLYLINE) — read-only overlap, no conflict.
- **Shipped T1-05 page-switch disarm**: leaves tool NONE with a draft set;
  Part 2 makes P resume that draft. A draft's vertices are PDF-space and
  commit to the *current* page — resuming on another page can commit
  cross-page geometry. Pre-existing (the dialog path allowed the same);
  unchanged risk, now at least not silently *replaced*.
- **Active type deleted while armed**: item-details.js:228 clears
  `activeLineTypeId` + tool on delete; the in-flight draft keeps its stamped
  `lineTypeId` — a deleted-type polyline lands in "Unassigned", same as any
  orphaned line today (reconcile paths handle it).
- **Quick Keys / Chain synergy**: 1-0 arms LINE with a bound type; P then
  starts a polyline of that same type — intended. Chain (T) is untouched
  (its own tool + palette).
- **`state.quickLineStart`**: the immediate path leaves it as-is, byte-parity
  with today's dialog path (tool change makes it moot; `setActiveLineType`
  clears it on the next LINE re-arm).
- **Disabled-button discoverability**: `#polylineStart` greys only when the
  explanation (`#polylineEmpty`) is showing directly above it — the picker's
  proven empty-state pattern, not a bare disable.
- **render-pixels.spec.js**: seeds annotations directly, never the arm path —
  baselines cannot move. Included in the local run as a tripwire.

## Acceptance criteria

1. With a line type active on a scaled page, pressing P (or clicking the
   toolbar/sidebar Polyline button) starts vertex placement immediately — no
   dialog; the finished run carries the active type's id and color, is named
   "Polyline N", counts in that type's tally, and never appears under
   "Unassigned".
2. Finishing (Enter / double-click / Finish / Close Polygon) behaves exactly
   as today (commit, tool → Move); one P press starts the next run with no
   dialog.
3. With no active line type, P opens the New Polyline dialog exactly as today,
   and Start Drawing works for a selected type.
4. With zero line types, the dialog shows the "—" select, the picker's
   "Add a line type first using **Create** or **Quick**." copy, and a disabled
   Start Drawing; no route exists to commit a `lineTypeId: null` polyline
   (forced-click guard included).
5. Pressing P mid-draw (or after a page-switch disarm) resumes the in-flight
   draft — vertices are never silently discarded by the arm path.
6. Unscaled page: P still shows the Set-Scale toast and arms nothing, both
   with and without an active type.
7. Staged Esc (T2-02), M-abandon, viewer gating, right-click Line Type
   settings, and Quick Line behavior are byte-identical to today.
8. `npm run check` passes (incl. build:guides + build:sw freshness);
   `polyline-arm.spec.js`, updated `snap-angles.spec.js`, and
   `polyline-esc.spec.js` green.
