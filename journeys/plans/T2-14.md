## Problem (verified)

Double-click (and mobile double-tap) rename on a sidebar sheet row is dead. Verified
chain: the row's `div.onclick` (features/pages-list.js:52) sets `state.currentPage` and
calls `App.fitZoom()` → `renderPdf()` + `updateUI()` (app.js:2036-2037) →
`App.renderPagesList()` (app.js:2451) → `el.innerHTML = ''` (features/pages-list.js:30),
synchronously destroying the `.name` node that holds both the `dblclick` listener and the
400ms double-tap timer closure (`onDoubleTapOrDblClick`, app.js:2626-2635, bound per-row
at features/pages-list.js:73). The second click lands on a fresh node whose timer is 0 —
the gesture is unwinnable, on active and inactive rows alike. The working path (single
click on the page-number badge, features/pages-list.js:71-72, which `stopPropagation`s
before the rebuild) is advertised only by a hover tooltip a tablet user never sees.
Users conclude sheets can't be renamed (J2 naive attempt: 2 wrong turns before the
tooltip was noticed).

## Design

One file: **features/pages-list.js**. Replace the per-row death-prone binding with one
delegated double-activate detector on the `#pagesList` container (static in
app/index.html:305 — only its `innerHTML` is ever cleared, so a listener on it survives
every rebuild). This is the shortlist's "defer past the dblclick window" applied to the
*rename detection* instead of to navigation, so single-click page switching keeps zero
added latency, and the row `onclick` (including its refit-on-active-row behavior) is
untouched.

1. Module-level state (beside `formatPageTitleStartEnd`):
   `let renameByPage = [];` (page index → that render's `openRename` closure) and
   `let lastNameTap = { idx: -1, t: 0 };` plus a `delegatedInstalled` flag.
2. In `renderPagesList`: reset `renameByPage = []` before the `state.pages.forEach`;
   stamp `div.dataset.pageIdx = i;` on every row; inside the existing `if (showEdit)`
   block set `renameByPage[i] = openRename;` and **delete** line 73
   (`App.onDoubleTapOrDblClick(div.querySelector('.name'), openRename)`). Call a new
   `installDelegatedRename(el)` once (guarded by the flag) before the loop.
3. The delegated handler — one `click` listener on `#pagesList`:
   ignore `e.target.closest('.page-num-badge-wrap')` (the badge keeps its own
   single-click rename; its inner listener already `stopPropagation`s); resolve
   `idx = Number(e.target.closest('.sidebar-item')?.dataset.pageIdx)` (works even when
   the clicked node was detached by a mid-dispatch rebuild — `closest` walks detached
   trees, and `dataset.pageIdx` makes index recovery independent of DOM position under
   `hideUnmarkedPagesFromSidebar`); if `idx === lastNameTap.idx` and `< 400` ms elapsed
   (the same literal window as app.js:2631), `e.preventDefault()`, reset the tap state,
   and call `renameByPage[idx]` if set — the closure rebuilt during THIS click's own
   rebuild, referencing the freshly appended row. Otherwise record `{ idx, t: now }`.

Why this works: click 1 navigates + rebuilds as today; click 2 bubbles from the (possibly
re-detached) row up to the persistent container, whose module-scope timer survived, and
opens `App.startRename` on the current DOM. Rename-edit interactions never reach the
handler — the input and the delete button both `stopPropagation` (app.js:2675, :2658).
Viewers get nothing (`renameByPage` stays empty when `showEdit` is false). Two quick
clicks on *different* rows reset the window and just navigate.

**What does NOT change:** the row `onclick`/navigation and its active-row refit;
badge-click rename + delete flow; `App.onDoubleTapOrDblClick` itself stays in app.js
(features/lines-list.js:154 still consumes it); `startRename`; no new `App.*` publishes,
no app.js edits, no CSS, no markup.

**Simplicity budget:** repairs a dead affordance with zero new UI, words, or settings —
N per-row listeners (2 per editable row) collapse into 1 delegated listener; kills the
rejected fallback (a visible pencil icon) by making it unnecessary; makes the guide's
existing "rename later from the Pages list" sentence true as written and ends the
tooltip-only discovery of rename (spirit test 4: double-click-to-rename is the file-
explorer convention plumbers already know).

## Tests

House naming: `*.spec.js` = Playwright; extend the owning spec **pages-list.spec.js**
(same fixture `test-2pages.pdf`, same console-error guard). New test(s):

- Double-click an **inactive** row's `.name` → navigates there AND `#pagesList
  .rename-input` appears; type `P-101 Underground` + Enter → row text and
  `state.pages[i].label` updated.
- Double-click the **active** row's `.name` → rename input appears.
- Control: a single click navigates and, after a 450ms wait, no `.rename-input` exists;
  two quick clicks on two *different* rows open no rename.
- Regression: badge single-click still opens rename + trash (the J2 control check).
- Viewer gate: with `state.isViewer = true` + `App.updateUI()`, double-click does nothing.

No Node unit test — no pure logic moved (matches the feature-file convention).

## Risks & edge cases

- **Shipped Tier-1 interaction (T1-05):** `recheckScaleGateOnPageSwitch` now runs inside
  `renderPdf` (app.js:1319) and can fire an *extra* `updateUI` rebuild during click 1
  when an armed line tool hits an unscaled sheet. The delegated design is rebuild-proof
  by construction — arbitrary intermediate rebuilds only refresh `renameByPage`.
  Verified: `renderPdf`'s async raster completion calls no `updateUI`/`renderPagesList`,
  so the opened input is not destroyed by the late paint.
- **Pending `scheduleUpdateUI` (app.js:2053, 120ms debounce)** firing after the input
  opens would rebuild and drop the edit — a pre-existing exposure shared byte-for-byte
  with today's badge-click rename; not made worse, not fixed here.
- **T2 units:** T2-01 (Clear Page) chose routes that don't touch pages-list.js
  (grep-verified); T2-15 (#26 thumbnail trim) lives in features/prepare-pdf.js — no
  overlap. If a later unit adds row controls, it must follow the badge's
  `stopPropagation` pattern or the delegated guard list grows.
- **Same disease elsewhere (out of scope):** features/lines-list.js:154 has the identical
  bind-then-rebuild pattern (its rows call `fitZoom`/`updateUI` too), but a visible edit
  pencil gives it a working affordance; this plan's delegated pattern is the template if
  it's ever repaired.
- **Truncated titles**: dblclicks on `.name-line-start`/`.name-line-end` spans resolve
  via `closest('.sidebar-item')` — covered.
- Desktop double-click may flash a text selection before the input replaces the label —
  cosmetic; the second click's `preventDefault` matches the old handler's behavior.

## Acceptance criteria

1. Double-clicking any sheet row's name — active or inactive, 200-sheet set or 2 —
   opens the inline rename input on that sheet; Enter commits (label + `markProjectDirty`

2. Double-tap (two clicks < 400ms) does the same; two quick clicks on different rows
   just navigate.
3. Single-click navigation is byte-identical to today: immediate, no delay, active-row
   click still refits zoom; badge-click rename + delete unchanged.
4. Viewers (`state.isViewer`) get navigation only — no rename from any gesture.
5. Extended pages-list.spec.js passes with zero console errors; `npm run check` passes
   (build:sw stamp regenerated).
